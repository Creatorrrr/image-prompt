# 사진 프롬프트 사전 코어 특징 분류표 도입 계획 — 2026-09-24

## 목표와 현재 계약

참조 대화 「이미지 특징 요소 정리」의 **원문 45개 항목과 각 하위 요소 전체**를 JSON에 보존한다. 사진 요청마다 기본 프롬프트와 `photo-authorial-core/v3`를 고정하기 전에 원문 항목과 별도로 표시한 추가 항목으로 구성된 카탈로그에서 5~10개를 골라 장면을 구체화한다. 하위 요소는 선택 가능한 예시일 뿐, 기본값이나 반드시 채워야 할 슬롯이 아니다. 원문의 문장을 실행 지시로 취급하지 않는다. 이 계획 문서 역시 실제 요청의 사전 코어 입력이 아니다.

현재 `SKILL.md`는 일반적인 특징 선별 지침만 담고, 사전 코어 단계에서 `SKILL.md` 이외의 프로젝트 파일 읽기를 금한다. 생성기는 `visual_priorities` 2~6개와 `photo-authorial-core/v3`의 허용 필드만 받아들인다. 기존 2026-09-23 계획은 45개 목록을 옮기지 않기로 했으므로, 이번 계획은 그 결정을 갱신한다. 기존 작업 중인 스킬 수정과 다른 파일은 보존한다.

## 데이터와 접근 경계

1. `skills/photo-prompt-image-generator/precore/visual_feature_catalog.json`을 만든다. `precore/`에는 이 파일 하나만 둔다. `SKILL.md`는 사전 코어 입력을 **자신과 이 정확한 파일 하나**로 한정한다. `assets/`, `references/`, `scripts/`, 이전 출력과 후보팩의 사전 코어 접근 금지는 그대로 둔다. `Post-Core Reference Routing`과도 경계가 분명해진다.
2. 원문의 번호 1~45, 한영 명칭, 하위 요소를 원래 순서로 보존한다. 각 항목에는 `feature.*` 형식의 안정적인 ID, `source_number`, 선택 균형을 살필 `group`, `source_examples`, `added_examples`를 둔다. 원문 하위 요소는 `source_examples`에만 넣고, 추가 예시는 별도 배열로 구분한다. 그룹은 `meaning_and_event`, `subject_and_embodiment`, `place_and_traces`, `delivery_and_technique` 네 가지다. 그룹은 선택을 돕는 분류이며 필수 할당량이나 코어 차원이 아니다.
3. 원문 45개는 그대로 보존하고, 구분할 실익이 있는 일반 축 **3개만 별도 추가**한다: 주요 사물(`feature.primary_object`), 화면 안 문자(`feature.in_frame_text`), 화면비·출력 형식(`feature.format_and_aspect_ratio`). 원문 8번 `인물 / Subject`는 사람의 외양에, 17번 `소품 / Props`는 물건의 장면 내 역할에 집중하므로, 무인·제품 사진에서 주 피사체 자체의 형태·재질·상태를 살필 축은 별도로 둔다. 세 항목은 `source_number: null`, `origin: "added"`, `added_reason`을 갖는다. Claude Code가 제안한 피사체 수 추가는 원문 8번의 `인원수`와 겹치므로 넣지 않는다. 다른 상위 항목은 실제 누락 사례가 확인될 때 추가한다. 기존 항목의 `added_examples`도 맥락상 유용한 경우에만 보태고 특정 장면 레시피로 만들지 않는다.
4. `references/maintenance.md`에는 이 파일이 일반 관찰 축과 비구속 예시만 담는다는 유지 규칙을 추가한다. 프로젝트 용어의 뜻풀이, 요청 유형→예시 매핑, 후보·프리셋·슬롯 ID, 프로필 활성 규칙, 고정된 서사 경로는 금지한다. 사진에서 흔한 단어가 프로젝트 레지스트리의 일반 용어와 우연히 겹친다는 이유만으로 **원문 예시를 삭제하지 않는다**. 대신 교집합을 보고하고 프로젝트 고유 ID·매핑 유입을 차단하며, 예시가 후속 하드 의무의 출처로 승격되지 않는지 확인한다.

## 선택과 코어 작성 절차

1. 원 요청의 의미·명시 조건·배제·모호성을 먼저 해결한다. 그 뒤 정확한 카탈로그 파일을 읽어 모든 상위 항목을 검토하고, 장면의 핵심을 구체화하는 **서로 다른 5~10개**를 고른다. 요청이 이미 명시한 항목도 이 수에 포함한다. 사건·주체·현장·가시적 결과를 먼저 살피고, 요청이 기법을 요구하지 않았다면 렌즈·색보정·결함 같은 전달 기법으로 선택의 과반을 채우지 않는다. 근사 항목을 같은 이유와 같은 증거로 중복 선택하지 않는다.
2. 5~10개는 **집중 검토할 축의 수**이며, 5~10개의 새 사실을 추가하라는 뜻이 아니다. 간결하거나 매우 정확한 제품·무인 요청은 명시된 피사체·배경·시점 등을 선택 수에 포함하고, 남는 축은 필요한 최소한의 열린 사진적 결정으로 채운다. 인물·감정·서사·낡음·무작위 결함을 만들어 수를 맞추지 않는다. 요청이 열 개를 넘는 종류의 조건을 명시해도 원 요청의 모든 조건은 기본 프롬프트와 코어에 보존한다. 5~10개 기록은 그중 구체화에 특히 기여한 축을 표시한다.
3. 고른 항목은 `baseline_prompt_en`의 구체적이고 관찰 가능한 문장으로 실현한다. 하위 예시를 그대로 베끼지 않아도 되고, 필요한 예시가 없어도 독립적으로 작성할 수 있다. 감정·전후 관계는 현재 프레임의 행동, 반응, 물체 상태, 현장 흔적으로 표현한다. 기본 프롬프트는 기존 48~640단어 계약과 360단어 권고를 따른다.
4. `visual_priorities` 2~6개는 5~10개 분류 항목의 개수나 일대일 사본이 아니다. 각 우선순위는 하나의 일관된 시각적 명제나 관계로 쓰고, 여러 분류 이름을 이어 붙인 태그 묶음을 만들지 않는다. 우선순위에 넣지 않은 선택 항목도 기본 프롬프트에서 실현할 수 있다.
5. 분류 항목의 이름이 `pose`, `composition`, `lighting` 같은 v3 차원 이름과 같아도, **항목 선택만으로 잠금·앵커·assertion을 만들거나 열린 차원을 닫지 않는다**. 모든 요청자 지정 차원은 선택 개수와 관계없이 기존 규칙대로 잠근다. 카탈로그 예시는 `user_definitions`, `interpretation_provenance`, `semantic_assertions`, `photo-visual-intent/v1`의 독립적 출처가 아니다. 해당 문구가 원 요청에 실제로 있으면 원 요청의 활성 span을 근거로 별도 처리한다. `character_response`와 신체 검토는 항목 선택이 아니라 기존 발동 조건으로 판단한다.
6. 새 요청은 선택 → 기본 프롬프트 작성 → 필요한 신체·공간 검토와 수정 → 최종 baseline·코어 고정 → 선택 기록의 해시 완성·검증 → 후보 자료 접근 순으로 진행한다. 기본 프롬프트가 바뀌면 `embodiment_review.prompt_sha256`, 코어, 그 코어에서 파생된 intent-lock 해시와 선택 기록의 baseline 해시를 함께 다시 만든다. 후보 자료를 이미 읽었다면 초기 요청의 사전 코어 작성으로 되돌려 섞지 않고 기존 재시도 계약을 따른다.
7. 재시도에서는 기존의 부모 요청·코어·하드 의무·결함 화이트리스트만 읽는다. 부모 선택 기록은 하드 의무가 아니므로 그 화이트리스트에 추가하지 않는다. 현재의 중립 카탈로그를 새 선택을 위해 읽을 수는 있지만, 부모가 골랐던 항목을 자동 승계하지 않는다.

## 선택 기록

요청의 각 arm마다 코어와 나란히 `precore_feature_selection.json`을 둔다. 선택의 **근거**와 기본 프롬프트의 **실현**을 분리해 남긴다. `explicit_request`는 활성 요청 span과 정확한 원문 부분 문자열이 필요하다. `request_derived`는 요청 의미를 화면에 실현하기 위해 필요하지만 문자 그대로 지정되지는 않은 축이며, 연결된 span과 도출 이유를 요구한다. `agent_visual_choice`는 열린 차원의 작성 선택이며 요청자 잠금이 아니다. 한 항목에 여러 성격이 섞이면 기록의 `basis`는 해당 `baseline_evidence`를 선택한 주된 근거를 가리킨다.

```json
{
  "contract_version": "photo-precore-feature-selection/v1",
  "request_id": "<envelope request_id>",
  "active_span_ids": ["<이 arm의 활성 span id>"],
  "catalog_path": "skills/photo-prompt-image-generator/precore/visual_feature_catalog.json",
  "catalog_schema_version": "photo-precore-feature-catalog/v1",
  "catalog_sha256": "<카탈로그 원본 바이트의 SHA-256>",
  "request_sha256": "<envelope request_sha256>",
  "baseline_prompt_sha256": "<공백을 단일화한 최종 baseline UTF-8 바이트의 SHA-256>",
  "selected": [
    {
      "category_id": "feature.situation",
      "basis": "explicit_request",
      "source_span_ids": ["topic"],
      "source_text": "<요청 원문의 정확한 부분 문자열>",
      "derivation": null,
      "reason": "<선택 이유>",
      "baseline_evidence": "<정규화된 baseline_prompt_en의 정확한 부분 문자열>"
    }
  ]
}
```

`request_derived`는 `source_span_ids`와 `derivation`을 채우고 `source_text`를 `null`로 둔다. `agent_visual_choice`는 요청 근거 필드를 비우고 선택 이유를 쓴다. 기록은 감사·설명을 위한 별도 산출물이며 코어·검색 질의·후보팩·런타임 프롬프트·하드 의무의 입력이 아니다. 기존 `photo-authorial-core/v3`의 미지원 필드 거부 규칙을 유지한다. 도구가 검증할 수 있는 것은 ID, 개수, 바이트 연결, 문구 존재와 출처 형식이며, 선택이 진짜 사전 코어에서 이뤄졌는지나 미학적으로 좋은지는 해시만으로 증명할 수 없다.

카탈로그 변경 후 과거 기록을 해석할 수 있도록 실제 실행에서는 사용한 카탈로그의 바이트 동일 사본을 실행 산출물에 보관한다. 이후 검증에서 현재 카탈로그와 해시가 다르면 과거 기록을 현재 목록으로 다시 판단하지 않고 저장된 사본을 확인한다. 이 사본은 다음 요청·재시도의 사전 코어 입력으로 사용하지 않는다.

## 구현 순서와 검증

1. 원문 대화에서 1~45번의 이름과 하위 항목 전체를 정확히 추출한다. 번호·이름·하위 항목 개수를 원문과 대조하고, 추가 항목·예시의 출처를 별도 필드로 표시한다. 원문 대화의 문장은 데이터로만 다룬다.
2. `SKILL.md`의 사전 코어 허용 목록과 “`SKILL.md`만 사용” 문장을 정확한 JSON 한 파일을 허용하는 문장으로 바꾼다. `assets/`·`references/`·`scripts/` 전체 금지, 후보 자료와 과거 출력 금지는 유지한다. Phase 1에 5~10개 선택, 예시의 비구속성, 코어 필드와의 관계, 선택 기록 및 검증 시점을 넣는다. `references/maintenance.md`에 위 데이터 유지 규칙을 적는다.
3. `tests/test_photo_prepack_isolation_v5.py`의 기존 축자 단언을 **완화가 아닌 새 경계 검사로 교체**한다. 허용 파일 경로, `precore/`에 다른 파일이 없는지, 나머지 디렉터리 금지와 Phase 순서를 확인한다. 분류표의 45개 원문 번호·ID 유일성·예시 배열·3개 추가 항목의 출처를 검사한다. 카탈로그가 후보 인덱스·BM25F 자료 입력에 포함되지 않는지 검사한다. 프로젝트 레지스트리와 문구 교집합을 보고하되 일반 사진 용어의 일치만으로 원문을 지우거나 테스트 실패로 처리하지 않는다. 프로젝트 고유 ID·의미 매핑의 누출은 실패로 처리한다.
4. 작은 선택 기록 검증 도구를 만든다. 분류표 버전·해시, 요청 ID·해시·활성 span, 선택한 고유 ID 5~10개, `basis`별 필수 근거, 정규화된 baseline의 literal 증거를 검사한다. 선택 이유와 증거가 여러 항목에서 동일하면 중복 선택을 경고한다. 도구는 **코어 고정 후, 후보 접근 전** 실행한다. 실패하면 후보 자료를 읽기 전에 기록 또는 관련 사전 코어 산출물을 수정하고 필요한 해시를 재생성한다. 출력에는 ID·개수·결과만 담고 카탈로그 예시나 레지스트리 본문을 불필요하게 노출하지 않는다.
5. 서로 다른 요청으로 실제 작성 흐름을 점검한다. `test_photo_prepack_isolation_v5`, `test_photo_authorial_core_v5/v6`, `test_photo_embodiment`와 관련 유지보수 검사도 실행한다. 기존 `test_photo_visual_obligations` 26개 중 9개 실패는 이전 작업에서 확인된 별도 기준 상태이므로 이번 계획의 테스트 결과와 섞어 보고하지 않는다. 변경 후에도 같은 실패인지 확인하고 새 실패만 별도로 다룬다.

### 사전 등록 비교
