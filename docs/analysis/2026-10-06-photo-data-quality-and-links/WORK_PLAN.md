# 후보·시각 의미 데이터 점검과 연결 조회 작업 계획

작성일: 2026-10-06 · 구현 반영일: 2026-10-07 · P0–P3 결과: [IMPLEMENTATION.md](IMPLEMENTATION.md)

설계는 [DESIGN.md](DESIGN.md)를 따른다. 원래 설계 요청의 산출물은 두 문서였으며, 이후 요청에 따라 아래 P0–P3를 구현·검증했다. 문서 작성으로 원본 정비나 커밋·푸시가 완료된 것으로 취급하지 않는다.

## 1. 단계와 의존성

**P0 → P1 → P2 → P3 순서로 진행한다.** P1에서 구조 오류가 확인되면 원본을 정비하고 기존 유지보수 경로로 검증·게시한 후 P2에 전달한다. draft 진단은 오류가 있어도 보존할 수 있지만, 정상 연결 조회는 검증된 세대만 대상으로 한다.

| 단계 | 작업 | 산출물 | 완료 조건 |
|---|---|---|---|
| P0 기준 고정 | 실제 실행 루트·커밋·dirty 상태·등록표·런타임 세대·환경을 기록하고 기존 실패를 구분 | `BASELINE.json`, 입력 지문, 제한된 비교 입력/기준 출력 | 주 작업 폴더의 별도 변경 보존, 기준 세대 검증, 원본별 책임 확정 |
| P1 전체 점검 | draft/generation 입력, 원본 목록·출처, 기존 구조 검증과 중복·모호함 의심 수집 | inventory/findings, 우선 정비 목록, 첫 전체 점검 보고서 | 전체 등록 원본 집계 일치, 오류 원문 보존, error/review/info 구분 |
| P2 양방향 조회 | 명시적 member/association edge 추출, 역방향 목록, 세대 결합과 보고서 게시 | links, CLI 질의, SUMMARY, 관리 포인터 | 원본 edge와 생성 결과 대조 통과, 양방향 경로 일치, 세대 혼합·오래된 최신 조회 거부 |
| P3 검토·우선 정비 | 검토 기록과 stale 판정, 영향 큰 문제의 제한된 정비, 변경 보고와 유지보수 절차 | 검토 기록, 정비 diff/근거, 재검증 보고, 문서 | 관련 검토 무효화, 참조 이관 검증, 필요한 인덱스/세대 재생성, 회귀 결과 기록 |
| P4 관계 보강 | 필요한 부족 영역에 한해 관계 제안·의미 검토·번들 원본 보강 | 제안/채택 근거와 원본 변경 | 별도 후속 범위. 미연결 전량 해소나 자동 링크 채택을 요구하지 않음 |

전체 데이터의 의미 검토가 완료됐다는 결론은 P1 자동 점검이나 P2 연결 생성으로 내리지 않는다. 첫 실행 범위는 P0–P3이며 P4는 필요성이 확인된 후 별도로 진행한다.

## 2. 제안하는 구현 위치

아래 인터페이스를 구현했다. 실제 옵션과 현재성 구분은 [관리 도구 README](../../../tools/photo_data_maintenance/README.md)에 있다.

| 위치 | 책임 |
|---|---|
| `tools/photo_data_maintenance/cli.py` | audit/build/query/diff 명령, 입력 방식과 출력 디렉터리 지정 |
| `tools/photo_data_maintenance/corpus.py` | 등록표 재사용, 원본 수집, generation 로더 연결, 원본 위치와 문맥 확장 추적 |
| `tools/photo_data_maintenance/quality.py` | 구조 진단과 중복·모호함 검토 항목 생성 |
| `tools/photo_data_maintenance/links.py` | 두 종류의 edge, 양방향 인접 목록, 경로 조회 |
| `tools/photo_data_maintenance/reviews.py` | 관리 검토 기록, 내용 해시 결합, stale 판정 |
| `tools/photo_data_maintenance/report.py` | 결정적 JSON 본문, Markdown 요약, 해시·게시·현재성 검사 |
| `tests/test_photo_data_maintenance*.py` | 구조·관계·변경·게시 경쟁·의미 경계 검증 |
| `docs/data-maintenance/photo-data-review-decisions.ndjson` | 실제 검토가 생겼을 때 관리 판단을 기록 |

운영 assets에 관리용 스키마나 역방향 참조를 추가하지 않는다. 기존 런타임 기능의 재사용을 우선하며, 런타임 코드 수정이 필요한 경우 P0에서 변경 필요성과 영향 범위를 먼저 명시한다.

명령 형태의 예:

```bash
# 편집 중 원본의 진단. 검증·게시된 연결 조회로 사용하지 않는다.
python tools/photo_data_maintenance/cli.py audit \
  --source-root /ABSOLUTE/PATH/skills/photo-prompt-image-generator \
  --output /ABSOLUTE/PATH/audit-run

# 검증된 특정 세대에서 관리 보고서 생성.
python tools/photo_data_maintenance/cli.py build \
  --source-root /ABSOLUTE/PATH/skills/photo-prompt-image-generator \
  --runtime-store /ABSOLUTE/PATH/photo-runtime \
  --generation GENERATION_ID --output /ABSOLUTE/PATH/report-run

# 고정 보고서의 연결 경로 조회. 기본 출력에 세대를 표시한다.
python tools/photo_data_maintenance/cli.py query \
  --report /ABSOLUTE/PATH/report-run \
  --profile clamshell_dual_source_portrait_light
python tools/photo_data_maintenance/cli.py query \
  --report /ABSOLUTE/PATH/report-run \
  --candidate slot:light_shape:lit_clean_vertical_catchlight_pair
```

최신 조회에는 `--require-current`, 실제 `--source-root`와 `--runtime-store`를 함께 요구한다. 과거 세대는 명시적 고정 조회로 허용하며 최신 확인과 구분한다. 정상 출력 0, 구조/무결성/현재성 오류 1을 사용한다. 의미 검토 의심과 미연결 정보만 있는 보고서는 정상 종료하며 건수를 명시한다.

## 3. P1 이후의 정비 우선순위

| 우선순위 | 대상 | 처리와 증거 |
|---|---|---|
| 선행 해결 | 구조 오류·깨진 참조·ID 충돌·원본과 생성 필드의 모순 | 원본 diff, 영향 참조 목록, 기존 검증기 결과 |
| 첫 의미 정비 | 기존 명시적 연결의 모순, 주체·조건 혼동, 일부 요소를 전체 구현으로 설명하는 사례 | 해당 후보·번들·프로필 원문과 유지/수정 근거 |
| 중복 정비 | 대상·조건·의무가 동일한 실질 중복 | 대표/별칭/변형 판정, 참조 이관, 검색·활성화 영향 |
| 설명 보강 | 적용에 영향을 주는 외형·관계·조건의 모호함 | 관찰 가능한 요소와 반례, 필요한 근거, 이전/이후 비교 |
| 후속 보강 | 의도적으로 또는 아직 미연결인 항목 | 필요 영역의 관계 제안. 연결 개수 목표를 두지 않음 |

한 번에 모든 서술을 재작성하지 않는다. P1 결과에 따라 영향과 근거가 분명한 작은 변경 묶음을 만들고, 각 묶음에서 원본·파생 인덱스·검증된 세대를 함께 관리한다. 초기 계획에서 결함 개수나 정비 완료율을 추측하지 않는다.

## 4. 의미 있는 검증 사례

| 사례 | 기대 결과 |
|---|---|
| 한 프로필에 여러 번들, 한 후보에 여러 번들, 한 번들에 여러 프로필 | 모든 경로 보존, 양방향 조회 일치, 고유 항목과 경로 수 구분 |
| 같은 entry ID가 다른 슬롯에 존재 | 슬롯을 포함한 ID로 구분. 번들 참조가 모호하면 오류 |
| 원본·매니페스트 누락, 중복 JSON 키, 잘못된 참조/순환 | draft에서 원문과 위치를 수집. 정상 links 게시 차단 |
| 문장이 같지만 대상·조건·속성·의무가 다름 | 중복 제거나 동일 의미 확정 없음 |
| 짧지만 충분히 구체적인 후보, 추상 역할을 가진 후보 | 글자 수나 필드 개수로 일괄 결함 판정 없음 |
| 세로 캐치라이트 후보와 클램셸 번들 | 경유 연관만 반환. 조명 전체 충족이나 필수 활성화 자동 판정 없음 |
| 공동 의무/다대다 authored components | 기존 구성요소·증거·검증 기준과 순서 유지 |
| 같은 ID의 설명·조건 변경, 번들 구성원 변경 | 관련 검토만 stale, 과거 기록 보존 |
| 원본 파일 위치 변경과 내용 동일 | 출처 갱신, 안정 ID 유지, 의미가 동일하면 관련 검토 유지 가능 |
| 새 항목의 기존 항목과 중복 의심 | 변경 파일 밖의 비교 대상까지 발견 |
| 새 파일 미등록, 등록 파일에 새 행, 정상 미연결 | 미등록 진단 / 새 행 포함 / 미연결은 정보 |
| 잘못된 보고서 해시·세대·루트·레시피 결합 | 조회 거부 |
| 편집 중 입력 변경, 게시 도중 세대 변경, 늦은 게시자 | 완성된 최신 보고서로 활성화하지 않음 |
| 과거 보고서와 최신 조회 | 고정 과거 조회 허용, 최신 요구에는 적절한 불일치 오류 |

오류의 탐지뿐 아니라 정상 사례를 잘못 제거하지 않는지도 검증한다. 테스트가 생성기 구현을 그대로 복제한 기대값을 만들지 않도록 작은 수작업 그래프와 실제 원본 참조의 독립 대조를 함께 사용한다.

## 5. 회귀·데이터 변경·게시

P0에서 현재 기준의 알려진 실패와 환경 문제를 재현·기록한다. 기존 전체 테스트를 이 작업의 성공처럼 재분류하지 않는다.

관리 도구만 추가한 P1/P2에서는 관련 단위 검증, 전체 원본 점검, 기존 참조의 독립 대조와 제한된 동결 입력의 공개 후보팩 비교를 수행한다. 새로운 코드·의미 변경이나 실패 근거 없이 전체 검사를 반복하지 않는다.

P3에서 실제 원본이나 운영 코드가 바뀌면 기존 유지보수 계약에 따라 다음을 수행한다.

- 변경을 소비하는 의미/프로필 인덱스를 재생성하고 깊은 검증을 수행한다. 벡터는 텍스트·제공자·모델·차원·해시가 맞는 항목만 재사용한다.
- 협력 편집과 세대 게시 경로를 사용한다. 새 원본이 준비되지 않은 동안 오래된 결과를 최신으로 제공하지 않는다.
- 관련 회귀와 요구되는 전체 검사를 실행한다. 기존 실패는 원래 기준 재현 결과와 구분한다.
- 변경에 따른 의도한 검색·활성화 차이와 의도하지 않은 차이를 따로 기록한다. 과거 코어·팩·영수증·검증 기대값을 덮어쓰지 않는다.
- 이미지 API·픽셀 심사·사용자 수용 검증은 실제로 수행한 경우에만 별도 결과로 남긴다. 관리 기능의 기본 완료 조건에 포함하지 않는다.

실행별 증거는 `docs/research-evidence/photo-prompt/data-quality-links-YYYYMMDD/`에 보존한다. 생성물의 형식·참조 통과와 의미 검토 완료 수를 별도로 보고한다. 커밋·푸시·병합은 해당 요청의 권한과 범위에 맞춰 처리하며 주 작업 폴더의 별도 변경을 섞지 않는다.

## 6. 최종 납품과 범위

P0–P3의 납품은 전체 자동 점검 결과, 명시적 관계의 양방향 조회, 검토 기록과 변경 시 무효화, 우선 정비 내역, 검증 증거, 실행·유지보수 문서다. 구조 오류가 없다는 결과와 의미 검토가 남은 항목 수를 함께 제시한다.

P4를 수행하지 않아도 위 범위의 완료는 가능하다. 미연결 항목을 0으로 만들거나 모든 연결의 의미 타당성을 검토했다고 주장하는 것을 완료 조건으로 두지 않는다.

이번 문서 작성에서 확인한 사항은 기준 커밋의 등록 파일·항목 수, 기존 로더·검증·세대 관리 구조, 구현 경계다. 설계 시점에는 실제 점검·구현·정비를 수행하지 않았다. 이후 실행 결과와 제한된 의미 정비는 [IMPLEMENTATION.md](IMPLEMENTATION.md)에 기록했다.
