# EmbeddingGemma 2 텍스트 270M 내장 전환 계획

작성일: 2026-10-14, Asia/Seoul. 상태: 2026-10-14 사용자 실행 승인 후 구현·모델 설치·전체 재임베딩·검증·기본값 전환 완료. 상세: `2026-10-14-embeddinggemma2-local-migration-result.md`.

## 목표와 범위

`photo-prompt-image-generator`의 문서·질의 임베딩을 스킬이 직접 관리하는 로컬 EmbeddingGemma 2 텍스트 구성으로 전환한다. Ollama, LM Studio, 상주 서버, HTTP 포트, 임베딩 API 키 없이 기존 후보 검색과 검증 흐름이 실행되어야 한다. 현재 요청은 계획 작성이며 이 문서만으로 구현이나 활성 인덱스 전환을 시작하지 않는다. 단일 전환 목표이며 지속 연구 프로그램을 시작하지 않는다.

최초 설치는 고정된 모델과 의존성을 받는 온라인 준비 단계로 분리한다. 준비가 끝나면 모델이 없는 경우에도 검색 중 자동 다운로드하거나 클라우드로 우회하지 않는다. 인터넷이 없는 새 장비에도 설치해야 하는 경우를 위해 모델·의존성·설치 설명을 포함하는 오프라인 배포 묶음도 설계한다. 소스 Git에는 코드, 설정, 버전 잠금, 모델 매니페스트와 라이선스 정보를 관리하고, 큰 가중치·가상환경은 배포 묶음에 포함한다.

이번 범위는 텍스트 검색이다. 이미지·오디오·영상 임베딩, 미세 조정, 후보 의미 데이터 개편, 이미지 생성 품질 개선은 별도 목표다. 기존 BM25F, 요청 의미 동결, 문맥·소유자·방향·제외 조건, 선택·표현 한도는 유지한다.

## 확인된 현재 상태

- `photo_embedding_provider.py`의 `SPACE`는 `gemini / gemini-embedding-2 / 768`로 고정되어 있고 실제 실행은 `google-genai`의 원격 호출이다. 루트 `requirements.txt`에는 `google-genai>=1.0.0`만 있다.
- 현재 `assets/photo_candidate_search.json`과 압축 메타데이터 기준 전체 후보는 18,250개, 벡터 대상 positive record는 18,180개다. 수량은 착수 시 소스 스냅샷에서 다시 확정한다.
- 현재 실행 경로는 `photo_slot_queries` → `photo_slot_retrieval` → `photo_sharded_search`와 `SearchReader`다. 오래된 개별 semantic/profile index 빌더를 전환 대상으로 삼지 않는다.
- `photo_slot_queries.validate()`는 HTTP 200과 응답 해시를 요구한다. 로컬 모델을 추가해도 이 검증을 바꾸지 않으면 실행이 거부된다.
- 빌더와 reader는 전역 `SPACE`에 결합되어 있다. 상수만 교체하면 기존 Gemini 인덱스의 읽기·재사용이 막히므로 명시적인 모델 공간 선택과 별도 빌드 경로가 필요하다.
- `photo_sharded_search.cosine_rank()`의 유사도 하한은 `0.30`이다. 새 모델의 점수 분포를 확인하지 않고 그대로 채택하지 않는다.
- 현재 장비는 Apple Silicon arm64, 메모리 32 GiB이고 프로젝트 `.venv`는 Python 3.14.3이다. 추론 패키지의 실제 설치·실행 호환성은 아직 검증하지 않았다.
- 소스에 진행 중인 변경이 있다. 특히 `photo_search_layout.py`, `photo_candidate_corpus.py`, `photo_contracts.py`, `photo_role_proposals.py`, `photo_slot_semantics.py`, `prompt_generator.py`의 변경을 보존하고 착수 때 관련 변경자·활성 작업과 파일 상태를 재확인한다.

## 추천 구현

1차는 **공식 Sentence Transformers + Transformers + PyTorch를 Python 프로세스 안에서 호출하는 방식**으로 구현한다. 현재 Python 검색 코드와 직접 연결하기 쉽고 공식 모델의 pooling·projection·normalization 구성을 보존할 수 있다. 의존성은 스킬의 설치 도구가 관리하므로 사용자가 별도 모델 실행 앱을 설치할 필요가 없다. [공식 추론 안내](https://ai.google.dev/gemma/docs/embeddinggemma/inference-embeddinggemma-with-sentence-transformers)

`google/embeddinggemma-2`는 전체 740M 모델이며 `vision_config=None`, `audio_config=None`으로 텍스트 270M만 로드할 수 있다. 출력은 기본 768차원이다. **다른 모델의 768차원 벡터와 호환된다는 뜻은 아니므로 기존 Gemini 벡터는 재사용하지 않는다.** [공식 모델 카드](https://huggingface.co/google/embeddinggemma-2)

계획상 배치는 다음과 같다. 파일명과 내부 디렉터리명은 구현 중 기존 설치 관례에 맞춰 확정한다.

```text
skills/photo-prompt-image-generator/
  scripts/photo_embedding_provider.py       # 공통 입력·캐시·검증 및 명시적 backend 선택
  scripts/photo_local_embedding.py          # 로컬 모델 로드·배치 추론
  scripts/setup_local_embeddings.py         # 설치·무결성 확인·오프라인 준비
  references/local-embeddings.md            # 설치·장애·복구 설명
  embedding-runtime.lock.json               # 모델/패키지/추론 설정 잠금
  requirements-local-embeddings.txt         # 검증한 추론 의존성
  .runtime/embeddinggemma2/<revision>/        # 로컬 가중치·토크나이저·모델 구성
  .runtime/embedding-python/                 # 필요한 경우 스킬 전용 Python 환경
```

모델을 import 시점에 로드하거나 네트워크·GPU 작업을 수행하지 않는다. 유지보수 준비 단계나 요청 의미 동결 이후의 명시적 임베딩 실행에서 지연 로드한다. 한 프로세스에서 모델 인스턴스 하나를 재사용하고 여러 슬롯의 질의를 모아 배치 처리한다. 별도의 상주 프로세스를 만들지 않으므로 CLI가 종료되면 모델도 해제된다.

공식 설정으로 인코더를 끄는 것과 다운로드 파일에서 해당 가중치를 제외하는 것은 별개다. 텍스트 구성만 저장한 로컬 패키지를 만들고, 공식 원본과 출력 동등성을 확인한 뒤 배포한다. 토크나이저·특수 토큰·pooling·projection·normalization 모듈이 모두 포함되어야 한다. 파라미터 270M의 FP32 가중치만 산술적으로 약 1.08 GB이며, 패키지·캐시·실행 메모리를 포함한 실제 크기는 측정한다. 양자화 광고 수치를 실제 메모리로 간주하지 않는다.

CPU FP32를 기준 구현으로 잡고 Apple MPS의 지원·속도·결과를 비교한다. 공식 안내상 FP16은 사용할 수 없으며 BF16 또는 FP32를 사용한다. 지원되는 가속 장치에서만 검증한 BF16 설정을 선택한다. GGUF/llama.cpp·ONNX·MLX 등의 경량 경로는 참조 구현의 결과를 확보한 뒤, 설치 크기나 초기 로드 시간이 실제 병목일 때 비교한다. [정밀도 안내](https://huggingface.co/google/embeddinggemma-2)

## 작업 단계와 완료 산출물

### 1. 실행 가능성과 배포 구성 확인

- 관련 dirty 파일, 현재 인덱스·소스·런타임 포인터를 해시로 고정하고 새 모델 실험을 별도 경로에서 수행한다. 기존 `GOAL_PLAN.md`와 활성 인덱스를 덮어쓰지 않는다.
- Python 3.14.3에서 검증 가능한 PyTorch/Transformers/Sentence Transformers 조합을 확인한다. 호환되지 않으면 기존 환경을 건드리지 않고 지원되는 Python으로 스킬 전용 환경을 만든다. 기존 검색 코드의 `math.sumprod` 등 Python 요구도 함께 확인한다.
- 공식 모델 revision, 패키지 버전, 토크나이저, 모델 구성, 라이선스와 필요한 고지를 고정한다. 설치 시에만 네트워크를 허용하고 실행은 로컬 경로와 offline 모드로 강제한다.
- 한국어·영어·혼합 언어의 소규모 문서·질의로 실제 텍스트 270M 로드, 유한한 768차원 출력, 정규화, cold/warm 시간과 RSS를 측정한다.
- 공식 원본과 텍스트 전용 패키지의 출력, 디스크 크기, 새 디렉터리에서의 오프라인 재로드를 비교한다.

산출물: 검증한 버전 잠금, 모델 파일 매니페스트, 최소 실행 결과, 설치 크기·실행 메모리·속도 표. 이 단계에서 전체 인덱스를 재생성하지 않는다.

### 2. 로컬 provider와 입력 계약 구현

- `embed_query()` / `embed_documents()` 또는 동등한 역할 구분을 도입한다. query와 document를 같은 입력 형식으로 처리하지 않는다.
- query에는 `task: search result | query: `, document에는 `title: none | text: `를 적용한다. 제목을 도입한다면 제목 생성 규칙까지 별도 recipe로 고정한다. prefix 중복 적용을 막고 원본 본문과 실제 모델 입력 해시를 모두 보존한다. [공식 입력 형식](https://huggingface.co/google/embeddinggemma-2)
- 1차 출력은 768차원과 L2 정규화로 고정한다. 256/512차원 축소나 가중치 양자화는 초기 전환과 분리한다. 토큰 수는 prefix를 포함해 확인하고 초과 입력을 조용히 자르지 않는다.
- 모델 revision·가중치/토크나이저 해시·입력 recipe·출력 차원·정규화·정밀도/양자화 설정을 모델 공간 식별에 포함한다. 실제 라이브러리 버전·장치·배치 설정도 실행 증거와 캐시 식별에 기록한다.
- 내장 추론의 결과에는 실제 모델 실행 또는 검증된 cache hit, 입력/출력 해시, 실행 설정과 시간 정보를 남긴다. HTTP 성공을 가장하지 않으며 Gemini의 원격 요청 증거도 보존한다.
- 체크섬 오류, 파일 누락, OOM, NaN, 0벡터, 차원 불일치, 중단된 추론을 구분한다. 로컬 실행 실패를 이유로 Gemini API나 `keyword_only`를 자동 실행하지 않는다.

산출물: 실제 로컬 provider, batch 경로, 모델 공간별 캐시, 의미 있는 오류·중단·동시 호출 검증. 라이브러리 import와 모델 로드의 시점도 검증한다.

### 3. 검색·검증·런타임 계약 연결

- `photo_slot_queries.py`의 슬롯 독립성·core/controls binding은 보존하고 HTTP 전용 실행 검증을 backend별 증거 검증으로 바꾼다. 여러 슬롯을 배치해도 각 슬롯의 원래 입력·binding·벡터는 개별 검증한다.
- `photo_global_index.py`, `photo_search_layout.py`, `photo_search_reader.py`, 빌더가 활성 인덱스의 선언된 모델 공간을 명시적으로 다루게 한다. 다른 모델·revision·입력 recipe의 벡터나 캐시를 거부한다.
- `photo_runtime_sources.py`, publisher, receipt, `audit_global_retrieval.py`에 모델 패키지와 실제 추론 의존성의 식별을 연결한다. 현재 환경 식별은 Python/Unicode 중심이므로 모델 파일·추론 패키지 변경도 검출하도록 확장한다.
- 모델은 불변 패키지로 참조하고 모든 런타임 generation마다 가중치를 복제하지 않는다. 설치 위치가 달라도 같은 패키지를 식별할 수 있게 하고 추론 전 실제 로컬 파일 무결성을 확인한다.
- 기존 exact cosine, full-pool eligibility, BM25F/RRF, pruning certificate의 독립 재검증을 유지한다. 새 벡터로 routing certificate와 통계·shard closure를 다시 만든다.
- 기존 Gemini backend는 비교·명시적 복구용으로 유지하되 새 기본 경로는 검증 완료 후 로컬로 선택한다. 활성 모델 선택과 receipt는 같은 generation에 묶인다.

산출물: 로컬 hybrid 질의부터 candidate pack/receipt/audit까지 통과하는 실행 경로, 모델 혼합 및 모델 변조 거부 결과.

### 4. 공용 인덱스 전체 재생성

- 고정한 소스의 모든 positive record를 새 모델로 배치 임베딩한다. 현재 관측 수량은 18,180개이며 과거 candidate/profile 두 인덱스의 수량과 합산하지 않는다.
- 최초 전환에서는 Gemini 벡터 재사용이 0개여야 한다. 재개 시에는 새 모델·revision·실제 입력·recipe가 일치하는 체크포인트만 재사용한다.
- 기존 Gemini 인덱스와 포인터를 보존한 채 별도 출력 경로에 새 인덱스와 runtime generation을 만든다. 빌더의 provider 선택·출력 위치·중단 후 재개를 명시적인 CLI 옵션으로 제공한다.
- 모델 인스턴스 하나를 공유하며 배치 크기와 CPU thread 수를 예비 측정으로 정한다. 기존 원격 호출용 4~8개 worker를 그대로 모델 로드에 적용하지 않는다.
- source가 빌드 중 바뀌면 활성화를 막는다. 전체 벡터의 ID/text/recipe/space, 차원·유한성·정규화, coverage, shard checksum, lossless 저장과 pruning certificate를 확인한다.

산출물: 독립적으로 검증된 로컬 인덱스·빌드 보고서·재개 체크포인트. 아직 기존 활성 포인터를 바꾸지 않는다.

### 5. 검색 품질과 체감 비용 비교

가설: 공식 텍스트 270M의 로컬 추론으로 기존 후보 검색의 실용 품질을 유지하면서 임베딩 API 의존성을 제거할 수 있다. 대립 설명: 다국어 표현·방향/소유자/관계 구분의 약화 또는 초기 로드 비용 때문에 실용성이 떨어질 수 있다.

- 같은 소스, 같은 원본 질의·허용 후보 집합, 같은 BM25F/RRF와 의미 동결 조건으로 Gemini와 로컬을 비교한다. 각 모델의 올바른 입력 prefix 차이는 모델 시스템 차이로 명시한다.
- 비교군은 현재 소스와 일치하는 Gemini 인덱스로 재확인한다. 과거의 2026-10-12 결과를 현재 기준선으로 그대로 쓰지 않는다. 기존 API 결과를 재사용할 수 있는지 먼저 확인하고, 새로운 유료 API 비교가 필요하면 실제 필요 입력·예상 호출량을 산출한다.
- 기존 holdout와 한국어/영어 질의 자료를 재사용하되 tuning에 노출된 자료를 미사용 검증 자료로 표시하지 않는다. 과거 audit의 오류 유형과 fixture는 현재 ID·recipe·소스와 매핑되는지 확인한 후 회귀 사례로 사용한다.
- vector-only Recall@1/5/10, MRR 또는 nDCG와 실제 hybrid의 슬롯별 적합 후보 포함률·금지 후보 채택을 구분한다. 동의어나 중복 후보 때문에 exact-ID만 낮아지는 경우는 고정된 적합성 판단으로 따로 설명한다.
- 한국어·영어·혼합 입력, 의역, 부정, 좌우 방향, 색상 소유자, 의상 연결 구조, 머리 질감 등 혼동 사례를 각각 확인한다. 합성 질의와 모델 자동 판정은 실제 사용자 검색이나 독립적인 정답의 증거로 과장하지 않는다.
- 새 모델의 positive/negative score 분포로 `0.30` 하한을 평가한다. 조정이 필요하면 development 자료에서 정하고 고정된 비교 자료에서 양쪽 시스템을 재검증한다. 낮은 품질을 가리기 위해 임계값이나 정답 기준을 사후 완화하지 않는다.
- 전체 슬롯 준비·검색의 cold/warm P50/P95, batch throughput, 캐시 적중/미적중, model load 시간, peak RSS, 설치/인덱스 크기를 측정한다. 추론 kernel 시간만 체감 지연으로 보고하지 않는다.

**제안 채택 기준:** 한국어/영어별 vector-only Recall@5와 실제 hybrid의 적합 후보 포함률이 같은 조건의 Gemini 대비 각각 2 percentage points 이상 낮아지지 않아야 한다. 고정한 문맥·제외·소유자·방향 회귀 사례에서는 새로 발생한 금지 후보 채택이 0건이어야 한다. 이는 계획상 제안이며 첫 비교 전에 고정하고 결과를 본 뒤 완화하지 않는다. 표본이 차이를 판정하기에 부족하면 판정 불가로 남긴다.

지연·RSS의 수치 목표는 아직 실측 근거가 없으므로 1단계의 대표 전체 요청 pilot에서 실용 예산을 제안하고 본 비교 전에 확정한다. 기존 검색 품질 기준을 충족해도 그 예산을 넘으면 경량 backend·배치·프로세스 로드 전략을 검토하고 필요한 비교만 다시 수행한다. 초기 전환의 성공을 양자화나 이미지 생성 품질의 성공으로 확대하지 않는다.

### 6. 기본값 전환·설치 안내·복구 확인

- 모든 채택 기준을 통과한 코드·모델 패키지·인덱스를 같은 버전으로 묶어 로컬 backend를 기본 선택한다. 사용자 요청 실행과 post-core·검증 경계를 유지한다.
- 전체 closure와 원자적 publication을 검증한 뒤 manifest/runtime 포인터를 전환한다. 새 질의 공간과 활성 문서 공간이 어긋나는 중간 상태를 허용하지 않는다.
- 최초 설치, 모델 상태 점검, 재설치, 오프라인 묶음 설치, 전체 재임베딩, Gemini로의 명시적 rollback 명령을 문서화한다.
- 새 임시 설치 디렉터리와 API 키가 없는 환경에서 실제 요청을 실행한다. 네트워크를 차단한 상태에서 uncached 질의의 모델 추론·검색·candidate pack·audit까지 확인한다. 캐시 성공만으로 오프라인 추론을 입증하지 않는다.
- 모델 누락/변조, 중단 후 재개, 동시 요청, rollback을 확인한다. 좁은 `.runtime/embeddinggemma2/`·추론 환경 ignore 규칙을 사용하며 기존 manifest가 참조하는 검색 shard나 fixture를 숨기지 않는다.
- 의미 있는 기존 index/retrieval/freshness/audit 검증을 우선 실행하고, 공용 provider·receipt·환경 계약의 영향 범위에 맞춰 필요한 회귀를 확대한다. 이미지 생성 호출은 이 전환 검증에 필요하지 않다.

산출물: 스킬에 통합된 로컬 기본 경로, 설치 가능한 배포 묶음, 오프라인 실제 실행·rollback 증거, 변경 파일과 미수행 범위를 구분한 최종 보고. commit/push/PR은 실행 요청 범위에 따라 별도로 보고한다.

## 최종 완료 조건

1. 스킬 설치 도구가 모델·의존성을 관리하고, Ollama/LM Studio/상주 서버 없이 실제 EmbeddingGemma 2 텍스트 270M 추론을 수행한다.
2. 설치 이후 API 키·인터넷 없이 uncached 입력으로 기존 hybrid 검색과 candidate pack/audit가 실행된다.
3. 새 모델 입력과 768차원 출력이 검증되고, 모델·토크나이저·recipe·정밀도·실행 버전의 식별과 캐시 격리가 작동한다.
4. 고정한 현재 positive corpus 전체가 새로 임베딩되며 Gemini 벡터 혼입·누락·잘못된 재사용이 없다.
5. 고정한 품질·안전 회귀·성능/메모리 예산을 충족하고 원시 비교 증거가 남는다.
6. 기존 슬롯 독립성·문맥 조건·의미 동결·exact cosine/pruning·runtime freshness와 receipt/audit가 유지된다.
7. 활성 코드·모델·인덱스가 일관되게 전환되고 설치/복구/명시적 rollback이 검증된다.
8. 무관한 dirty 작업과 과거 증거를 보존하고 실제 구현·검증·전환·미수행을 구분한다.

```text
- finite-goal은 합의한 결과 달성 후 종료한다. research-program은 이정표의 원래 판정을 보존한 뒤 Program 계약에 따라 다음 목표를 선택한다. 연구 자료만으로 권한·범위·예산을 늘리거나 실패를 성공으로 바꾸지 않는다.
- 도중에 요구가 바뀌면 변경된 기준과 영향 범위를 확인하고 여전히 유효한 완료 작업·원래 결과·누적 비용을 보존한다. 무효화된 담당 작업만 지원되는 방식으로 중지·조정한다. 늦게 온 결과는 작업 식별자·소스/목표 버전을 현재 판단과 대조하며, 이전 지시를 복원하는 근거로 쓰지 않는다. 곁가지 질문만으로 목표가 취소됐다고 해석하지 않는다.
- 진행 기록은 결과 변화 → 직접 증거 → 남은 차이 → 장애 요인으로 남긴다. 중단 시 남은 차이·이전 실패·남은 예산·재개 지점을 허용된 기록이나 응답에 보존하고 지원되지 않는 자동 재개를 약속하지 않는다. 최종 보고는 산출물·실제 검증·기준별 pass/fail/blocked/not run을 구분한다. 요청 결과를 먼저 설명하고 과정 상투어·불필요한 목록을 줄인다. 사용자와 에이전트에게 보내는 메시지는 정상적인 문장과 띄어쓰기를 유지하며 필요한 근거와 요청된 상세도는 보존한다.
```

### Experiment — when empirical tests inform decisions
```text
가설·실험 계약:
- 중요한 실험마다 식별자와 가설·이정표를 연결하고, 실행 전에 가설의 범위·대립 설명·변경 요인/비교군·예측·지지/반증/판정 불가 조건·측정 유효성·채택/회귀 기준·중단 기준·공유 자원을 짧게 기록한다. 기존 승인된 로그나 세션 기록을 사용하며 새 프레임워크나 매 명령 보고서는 요구하지 않는다.
- 사전 기록은 결과에 맞춰 덮어쓰지 않는다. 변경은 버전·이유를 남겨 다음 실험에 적용하고 예비 탐색과 확증을 구분한다. 코드와 미커밋 상태·설정·데이터·평가기·실행 명령/조건·결과 위치를 연결하고 관련된 반복·seed만 기록한다.
- 실행 상태와 실험 유효성(valid/invalid/pending), 가설 판정(supported/refuted/inconclusive/not_tested), 구현 채택(adopt/reject/defer/not_applicable), 이정표 판정(pending/pass/fail/blocked/not_run)을 분리한다. 지원/반증 판정은 해당 주장에 대한 유효한 관측이 있어야 한다. 무효 실행은 보통 미검증, 유효하지만 근거가 부족하면 판정 불가이다. 실험의 유용함으로 이정표 성공을 만들지 않는다.
- 실행 오류·OOM이 무관한 과학 가설을 반증하지는 않는다. 자원 한도 내 실행 가능성이 사전 가설이었고 측정이 유효한 경우에는 그 한정된 가능성을 반증할 수 있다. 여러 변경을 묶어 성공했으면 각 변경의 인과 효과를 따로 입증했다고 주장하지 않는다. 개선 미확인이 언제나 효과 부재를 뜻하지는 않는다.
- 실제 관측·출처 주장·추론·미수행을 구분하고 실패 실행·반대 증거·편차·조건부 성과도 보존한다. 성능 비교는 같은 평가 조건에서 실질적인 기준과 필요한 변동성 검사를 적용한다. 작은 결정적 수정에 통계·독립 검토를 일률적으로 요구하지 않는다.
- 탐색에 쓴 평가와 최종 확인을 구분하고 프로그램 전체의 평가 노출과 선택 이력을 유지한다. 반복해서 후보 선택에 쓴 홀드아웃을 미사용 검증으로 부르지 않는다. 독립 확인 자료가 없으면 주장 범위를 제한하거나 탐색 결과로 표시하며 새 데이터 수집을 자동 의무화하지 않는다. 평가기를 고치면 별도 버전과 근거를 남기고 기준선·후보를 같은 버전으로 재비교한다.
- 중요한 비교의 고비용 실행 전에 문서상 비교군과 실제 생성된 구성·동작을 대조한다. 관련 구성/버전·변경/동결 범위·상태 공유와 초기화 경계·초기 조건·입출력/채점/갱신 순서를 적용 가능한 만큼 확인하고 후보와 비교군의 실제 차이를 기록한다. 이름·설정 파일만으로 실행 구조를 단정하지 않으며, 선언과 실제가 어긋나면 영향을 받는 비교만 보류한다. 기존 소규모 재현이나 구성 출력으로 충분하면 새 도구·DB를 만들지 않는다. 점검표·해시 일치는 의미적 정확성의 증명이 아니다.
- 단일 요인의 효과, 여러 변경의 결합 효과, 공통 기준선 대비 시스템 성능을 구분한다. 초기 조건·데이터·평가·상태 초기화 등 통제 조건이 다른 비교로 개별 요인의 인과적 기여를 주장하지 않는다. 필요한 최소 추가 비교 또는 결론 범위 축소를 택하고, 이미 나온 수치와 해석의 유효성을 분리해 원본을 보존한 정정 기록을 남긴다.
- 실행 목적을 탐색·실패 원인 진단·승격 확증으로 구분한다. 개발 게이트 실패 뒤 진단은 원래 실패를 유지하고 어떤 결과가 어떤 다음 결정을 바꾸는지, 최소 비교·공유 자원·종료 조건을 실행 전에 기록한다. 필수 게이트를 우회하거나 진단 결과로 승격하지 않는다. 위임된 범위 안의 진단은 기존 권한으로 수행하며 새 비용·기준/범위 변경에만 해당 승인 경계를 적용한다. 아무 결과도 결정을 바꾸지 않는 반복은 하지 않는다.
- 중요한 주장 검증자는 가능하면 원래 질문·기준·실제 코드/구성과 원시 증거를 먼저 읽고 독자 판정을 남긴 뒤 작성자의 결론과 대조한다. 핵심 구현·비교 의미·반대 증거·미수행을 확인한다. 별도 세션/모델은 지원·권한이 있을 때만 쓰며, 순차 자기검토를 독립 검증으로 표현하지 않는다. 실험/평가 코드는 권한 범위에서 분리·고정하고 변경 시 비교 양쪽을 재검증한다.
- 결과마다 실제로 바뀐 메커니즘과 검증한 능력을 연결한다. 전처리·규칙·보정·외부 도움·런타임 개선을 다른 핵심 능력의 증명으로 바꾸지 않는다. 단순 기준선과 목표 능력에 맞는 지표로 확인하고, 진단용 입력이나 제한된 조건의 성공을 최종 경로·일반화로 자동 승격하지 않는다. 확률 보정만으로 상황별 예측의 정보력을 주장하지 않는다.
- 중요한 채택은 영향과 불확실성에 맞는 재현·독립 확인을 사용하고 검증된 최선 산출물을 보존한다. 남은 필수 검증이 있으면 pilot을 최종 개선으로 선언하지 않는다. 실험 중간 기록은 성공 보고서 자격과 무관하게 남길 수 있고, 정식 passed 보고서는 판정 대상 이정표의 모든 최종 기준과 기존의 닫힌 자격 조건을 충족할 때만 작성한다.
- 새로운 영역이나 평가기를 준비할 때는 후보 인터페이스·바꿀 파일·실운영 조건·필수 제약·보호할 평가/데이터/기준선을 먼저 정의하고, 해당 평가가 정상 기준선과 명백히 잘못된 대조를 구분하는지 필요한 최소 확인을 한다. 후보가 자신의 채점 기준·보호 데이터·비교군을 몰래 수정해 통과하지 못하도록 지원되는 격리/검증 경계를 사용한다.
- 고비용 탐색은 필요한 경우 값싼 문법/불변 조건·작은 실행·동일 조건 개발 평가·비례적인 확증 순으로 나눈다. 단계별 측정과 추가 비용을 보존하며 파일/설정/데이터/정밀도/규모/환경이 바뀌면 비교군을 분리하거나 같은 조건으로 재비교한다. pilot 수치를 confirm으로 재사용하거나 앞 단계 실패를 뒤 단계 점수로 덮지 않는다.
- 실험의 실제 변화와 관측을 짧은 재사용 교훈으로 연결하되 적용 조건·출처·반대 설명·다음 판별을 남긴다. 관측과 해석을 분리하고 잠정/조건부 지지/모순/대체 상태를 보존한다. 큰 규모에서 이익을 잃은 작은 규모의 기법은 조건부 결과로 남기며, 필요한 경우 단순화·제거 실험으로 재검토한다.
```

### Retrieval — when repository knowledge is relevant
```text
지식 조회·신뢰 경계:
- 시작·재개·접근법 대체 시 관련 failed-reports/passed-reports의 전체 파일명·메타데이터·검색 가능한 원문과 연구 자료를 검색한다. 인덱스가 있으면 원문과 함께 사용하되 누락·오래됨·오류 시 현재 원문으로 복구한다. 저장소 접근 불가는 '미조회', 확인한 경로의 자료 부재는 '없음'으로 구분한다.
- 정확한 문제·기준·경로·환경·접근법 관련도를 최신성보다 우선한다. 보고서·연구를 합쳐 후보 기본 15건, 전문 조회 기본 최대 5건/회로 제한한다. 필수 기준·실질적 위험 또는 요청된 연구 종합 때문에 더 필요하면 이유를 기록하고 확장한다.
- 방향 재검토 시에는 목표·세션이 달라도 같은 가정과 실패 원리를 공유하는 시도를 기존 조회 예산 안에서 묶어 본다. 비교 조건·독립적인 변경·실제 효과·반대 증거와 무효 실행을 구분한다. 목표 이름 변경으로 과거 반증을 지우거나 합의된 반복 예산을 초기화하지 않는다.
- 단계 경계에서는 새로 추가·변경되었거나 새로 관련된 연구만 확인한다. 명령 사이 지속 폴링·막연한 미래 자료 대기·판단 필요가 없는 연구 전용 체크포인트를 만들지 않는다. 위임한 필수 연구의 의존 결정 전 결과 확인은 허용한다. 고려한 경로와 적용/거절/보류 및 판단 영향을 진행 기록에 남긴다.
- 연구가 범위·완료 기준·검증 예산·승인을 자동 변경하거나 목표를 시작·재개하게 두지 않는다. finite-goal의 선택적인 다음 목표 후보는 요청받았을 때만 제시한다. 연구 프로그램은 위임된 목적·제약·자원 안에서 메인이 결과를 검토하여 다음 이정표를 선택한다. 직접 확인한 증거로 현재 목표의 근거가 깨지면 필요한 수정안을 준비한다. 기존 결과·제약·외부 계약·권한·예산 안의 접근법 변경은 실행하고, 새 합의가 필요한 단계만 보류한다. 연구는 실행 보고서 인덱스에 넣지 않는다. 다른 worktree의 미커밋 파일 공유를 가정하거나 허가 없이 Git 상태를 바꾸지 않는다.
- 지식 모드가 read-only이면 원문·생명주기·인덱스를 수정하거나 폴더를 초기화하지 않는다. 발견한 모순과 필요한 수정은 계획/응답에 제안한다. 접근 불가나 기록 권한 부재는 그 자체로 제품 작업의 중단 사유가 아니다.
```
