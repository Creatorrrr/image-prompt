## 1. 반론 수용 여부 — 6건 모두 수용

**#5 (코드 범위 누락) — 제 오류 확정. 코드로 검증했습니다.**
`generations/9649504f…/scripts/photo_h_f2_generation.py`의 `stage()`:
- L46–50: native record의 `rf.documents(record)` parts에서 `expected`를 **재구성**하고 `rf.require(d['text']==expected and d['text_sha256']==rf.sha(expected), 'D text or lookup cues changed')`
- L52–60: 같은 parts에서 `expected_fields`를 **재구성**하고 `rf.require(f['fields']==expected_fields, 'D part field ownership changed')`
- L62: `proof['input_sha256']==rf.sha('title: none | text: '+expected)` — **임베딩 입력까지 expected D로 고정**
- L69: `rf.require(Counter(rf.tokens(d['text']))==Counter(...f['fields']...), 'field token loss')`

즉 저장 포맷이 파일로 분리돼 있다는 제 관찰은 맞았지만, **builder/검증기가 두 lane을 같은 파생으로 강제**합니다. `project()`만 고치면 `stage()`가 세대 생성을 거부합니다. "한 함수 수정"은 틀렸고, 초안 2단계의 "컴파일러 + 새 builder/검증기/manifest 계약 + 코드 binding" 범위가 맞습니다. (부수적으로: 이 때문에 기존 C 파일럿도 설치 builder로는 staging될 수 없었을 것이며, v2는 순수 신규 구현입니다.)

**#1 (외삽/인과 주장) — 수용, 철회합니다.** 전수 보강은 모든 문서의 벡터와 모든 term의 DF/avgdl을 바꾸므로 41건 섭동에서 전역 경쟁 재편을 예측할 수 없습니다. 96건은 positive 포함 층화 표본이고 처치 간 순위 간섭(SUTVA 위반)이 있어 +3/−3 어느 쪽도 비편향 처치효과가 아닙니다. "+7~+17"과 "미보강군 손실은 전수 시 사라진다"를 철회합니다. 또 제 "효과 측정 불가능"이라는 표현도 부정확했습니다 — 파일럿은 **이 부분 처치가 이 경쟁 조건에서 낸 순효과를 정확히 측정했고**, 다만 전수 효과를 식별(identify)하지 못할 뿐입니다. 남는 것은 "노출 부분집단 17→20/21"이라는 **기술 통계이자 가설 생성 자료**뿐입니다.

**#2 (known-positive 누락 계상) — 수용, 철회합니다.** 제가 두 원칙을 뒤섞었습니다. "미판정을 negative로 세지 않는다"는 **대체 후보**를 어떻게 다룰지의 규칙이고, "알려진 positive가 top8에서 빠졌다"는 **그 positive에 대한 직접 관측된 recall 손실**입니다. 후자를 전자 때문에 지우면 recall이 조용히 부풀려집니다. 초안 문구("대체 후보의 판정 여부와 무관하게 알려진 적합 연결 손실로 센다")가 맞습니다.

**#3 (노출군 ≥20/30을 사전 gate로) — 수용, 철회합니다.** D1=21/30을 이미 본 뒤 그 값 아래에 사전 PASS선을 긋는 것은 전형적인 사후 gate 맞춤이며, 사용자가 명시적으로 배제한 방향입니다. 62/126·28/40 유지, subset은 설명 지표, 3단계는 구현 정확성 검증만 — 전부 동의합니다.

**#4 (융합 일반화) — 수용, 완화합니다.** 제가 측정한 것은 **unweighted RRF k∈{1,5,20,60,200} + lane quota 3종**, 단일 arm의 저장 점수, 126쌍입니다. weighted fusion, score 정규화 결합, lane별 보정, depth-aware 정책은 건드리지 않았습니다. "막다른 길"을 철회하고 "이번 라운드에서 융합을 고정할 우선순위 근거"로만 씁니다.

**#6 (query형/문서형 분류) — 수용, 철회합니다.** lane 순위는 **실패 위치**의 관측일 뿐 원인 귀속이 아닙니다. Q1 대조의 실제 효과로만 판단하는 초안 문구가 맞습니다.

## 2. 초안에 남은 실질적 구멍 7가지

**(1) L69를 제거할 때 대체 불변식을 명시해야 합니다 — 가장 위험한 편집.**
현재 L69는 "BM25F로 검색되는 모든 토큰은 실제 임베딩된 텍스트에도 존재한다"는 **날조 방지 속성**을 부수적으로 보장합니다. 분리하면 이 속성이 사라져, 사람이 읽는 어떤 문서에도 없는 텍스트가 sparse에만 색인될 수 있습니다. 초안 2단계는 "lane별 hash/pointer 결속"이라고만 적혀 있습니다. L69를 대체할 **단방향 2검사**를 명문화하십시오:
- sparse: 모든 필드 값은 `(native part) ∪ (승인된 review의 summary/alias)` 에서만 나오며, 값마다 원문 pointer 또는 review sha256이 결속된다. 둘 중 어디에도 없는 값 = 0건.
- dense: D1은 `expected D`와 정확 일치, D1b는 `expected D + 선언된 summary 연결`과 정확 일치. 임의 문자열 금지.

**(2) Q1은 새 query 벡터 12개가 필요합니다 — 초안에 누락.**
5단계는 두 lane이 같은 새 query를 쓰므로 해당 12개 목표의 **query 임베딩 12건이 신규 생성**됩니다. 문서 벡터는 불변입니다. "새 임베딩 0"이라는 서술이 3·4단계에만 해당함을 분명히 적어야 전체 비용 주장이 정확해집니다. (검색 횟수는 여전히 목표당 1+1, 총 75+75로 불변.)

**(3) Q1 대상 12개 목표의 처리 규칙을 지금 고정해야 합니다.**
초안은 "1단계에서 고정한 12개 0건 목표"(=A 기준)로 블라인드하게 잡았는데, 4단계 승자 기준으로는 그중 2개(holdout-01/body_pose, holdout-04/action)가 이미 회수된 상태일 수 있습니다. 결과를 본 뒤 대상을 조정하면 선택 편향입니다. **지금 둘 중 하나를 선언**하십시오: ⓐ A 기준 12개 전부 재작성하되 이미 회수된 목표의 결과를 별도 보고, 또는 ⓑ "승자 arm 기준 0건 목표"로 규칙 자체를 사전 고정. ⓐ가 더 블라인드합니다.

**(4) Q1 작성자의 사전 노출에 대한 guard가 약합니다.**
"과거 판정을 이미 접한 한계는 기록한다"는 정직하지만 검증 불가능합니다. 검증 가능한 장치로 바꾸십시오: 새 query의 **모든 절이 원 요청/장면 의도/슬롯 표현 목표의 pointer+quote에 매핑**되어야 하고, ① 출처 pointer 없는 절 = 0, ② 특정 CID에만 나타나는 어휘 = 0. 이 `QUERY-PROVENANCE.json`을 점수 산출 전에 봉인하면 작성자가 노출돼 있어도 감사 가능합니다.

**(5) Q1의 효과를 "더 나은 query"와 "그냥 다른 query"로 구분할 장치가 없습니다.**
query를 바꾸면 그 목표는 A와 동일 조건 비교가 불가능합니다. 비용 0의 보완: 1단계에서 이미 기록할 해당 목표들의 **양 lane positive 순위**를 이용해, Q1으로 새로 들어온 positive가 (ㄱ) 원래 심층(예: 100위 밖)에서 올라온 것인지 (ㄴ) 원래 9~16위권에 있던 것인지 분류해 보고하십시오. (ㄱ)이면 query 표현이 실제로 작동한 증거, (ㄴ)면 경계선 흔들림입니다.

**(6) 6단계의 판별력이 매우 낮습니다 — 무료로 개선 가능.**
목표 6개에서 "유용 소재 ≥1건"은 사실상 승자를 **탈락시킬 수만 있고 확인할 수는 없는** 지표입니다(초안도 "A가 6/6이면 유지 확인"이라 인정). 판정 수를 늘리지 않고 두 가지만 바꾸십시오:
- 새 요청 3건의 슬롯 구성을 **composition/lighting에 가중**되도록 사전 규칙으로 선택(현재 결손 71건 중 46건이 이 두 슬롯). 결과를 보고 고르지 않음.
- 지표 해상도를 올려 "목표당 유용 소재 **개수**"도 함께 기록(이미 top8 전부를 판정하므로 추가 비용 0).
또한 gate 2번의 경계 규칙("A와 동점이면 유용 연결 수로 비교", "6개 중 1개 미달이면 재추첨 없이 HOLD")을 **지금** 적어두십시오.

**(7) HOLD로 끝날 때 무엇이 자산으로 남는지 선언해야 합니다 — 전략적으로 가장 중요.**
사후 재결합 D1은 56/126입니다. 62까지는 +6이 더 필요하고, Q1이 겨냥하는 A 기준 0건 목표 12개가 보유한 positive는 총 **27건**입니다. 즉 "D1b + Q1이 +6을 만들어낼 것인가"가 이번 라운드의 사실상 유일한 승부처이며, **HOLD 확률이 낮지 않습니다.** 그것 자체는 올바른 설계이지만, 네 번째 연속 HOLD가 아무것도 남기지 못하면 안 됩니다. 초안에 한 문장을 추가하십시오: **2단계의 lane 분리 builder/검증기/manifest 계약은 품질 gate 결과와 무관하게 유지·커밋하며, 7단계 HOLD가 2단계 산출물의 revert를 의미하지 않는다.** 2단계는 이 계획에서 유일하게 가치가 gate에 종속되지 않는 단계입니다.

## 3. 동의하는 부분 (변경 불필요)

- 3단계를 **구현 정확성 검증 전용**으로 두고, 이미 아는 56/29를 사전 예측 성공으로 세지 않는 설계. 정확합니다. dense 벡터가 A와 동일함을 hash로 증명하더라도 **실제 1+1 검색을 생략하지 마십시오** — 그게 3단계의 존재 이유입니다.
- 4단계에서 "동률이면 더 단순한 D1 선택", "실패 후 요약 길이·alias·가중치 변형 추가 탐색 금지", "cosine 하락 2건 제한을 gate로 쓰지 않음". 제가 지난번에 제안한 "하락 ≤2"는 임의 숫자였으므로 진단 기록으로 내린 판단이 옳습니다.
- union8=66을 달성 가능한 Recall@8로 보고하지 않는다는 서술. 정확합니다(합집합 최대 16 CID, 슬롯 8개). "합집합 밖 적합 1건이 RRF로 들어왔다"는 관찰도 융합이 순손실만은 아님을 보여주는 좋은 기록입니다.
- 설치 cache의 봉인 코드를 직접 편집하지 않고 새 Git 소유 구현/세대를 만들며 기존 receipt는 원 세대에서 재생. 맞습니다. 8단계에 한 줄만 추가하십시오: **선택 manifest 복구(rollback) 경로를 전환 전에 실제로 테스트**하고, 전환 후 기존 run 1건의 receipt 재생을 확인.
- arm 3개(D1/D1b/Q1), 신규 원문 검토 0, 전수 보강 0, query/doc/fusion/model 동시 튜닝 금지. 범위가 적절합니다.

**한 가지 전향적 메모(이번 라운드 gate 변경 아님):** 사용자 목적("실사용 가능하면 완벽할 필요 없다")에 가장 가까운 지표는 pair recall 62/126보다 **0건 목표 수**(현재 A 12/40)입니다. 다만 이를 지금 gate로 바꾸면 결과를 본 뒤의 기준 변경이 되므로, **다음 라운드 계획에 사전 등록**하는 것이 올바른 순서입니다. 이번에는 62/126 ∧ 28/40을 그대로 두십시오.

## 4. 최종 권고

초안을 **승인합니다.** 위 (1)~(7) 중 **(1) 대체 불변식 명문화, (2) Q1의 query 벡터 12건 명시, (3) Q1 대상 목표 규칙 사전 고정, (7) HOLD 시 2단계 산출물 보존 선언** 네 가지는 구현 착수 전에 초안에 반영하십시오. (4)(5)(6)은 비용 0의 품질 개선이므로 함께 넣기를 권하지만 필수는 아닙니다.

실행 순서는 초안 그대로 **1 → 2 → 3 → 4 → (미달 시) 5 → 6 → 7 → (통과 시) 8**, CURRENT는 전 구간 유지. 그리고 3단계 이후 62/126에 못 미치는 것은 **예상된 경로이지 실패 신호가 아니라는 점**을 계획에 적어두면, 5단계 진입 때 기준을 흔들고 싶은 압력이 생기지 않습니다.
