## B. 같은 D를 두 lane에 쓰는 것이 적절한가 — **아니오, 그리고 분리는 이미 가능합니다**

### 결합의 실제 비용

`photo_candidate_documents.py:project()`는 `text = original + '\n' + additions`로 dense 입력을 만들고, 곧바로

```python
if Counter(tokens(text)) != Counter(t for values in fields.values() for v in values for t in tokens(v)):
    raise ValueError('field token loss or duplicate ownership')
```

로 **dense 텍스트와 BM25F 필드의 토큰 다중집합이 같아야 한다**고 강제합니다. 이 한 줄이 두 lane을 묶는 지점입니다. sparse에 유용한 별칭·동의어를 넣으면 dense 벡터가 그만큼 희석되고, 그 결과가 `cand_727d42f4301d59ea99094f5da0db7f20`의 cosine 1위→28위입니다.

### 무손실 보존과 검색 입력은 분리 가능합니다

"무손실"은 **정본 레코드의 속성**입니다 — 이미 Git 소유 정본으로 export됐고 전체 hash `c5cefec8f854b72a2e7053d0d38e681972d92172a863b39c1777869363e3e661`로 고정돼 있습니다. 검색 텍스트는 그 정본에서 파생된 **투영**이며, "D prefix를 무조건 보존"은 재현성 가드이지 무손실 요건이 아닙니다. 가드를 **lane별로** 재정의하면 됩니다: ① 정본 hash 불변, ② lane별 투영 레시피를 선언·테스트, ③ 각 lane 안에서 기존 D 단서가 prefix로 보존되는지 lane별 검사.

### 설치 포맷은 이미 분리돼 있습니다

설치된 generation `663038595155d8…`에는 **`documents.json.gz`(dense용)와 `field-documents.json.gz`(BM25F용)가 이미 별도 파일로 존재**하며 각각 CID별 엔트리를 가집니다. 즉 **런타임 포맷 변경이 필요 없고**, 바꿀 곳은 컴파일러 `project()` 한 군데입니다.

### "lane당 1회 검색" 제약은 전혀 깨지지 않습니다

제약은 **검색 호출 수**에 걸린 것이지 색인 표현에 걸린 것이 아닙니다. 분리해도 RID당 dense 벡터는 여전히 **1개**, 목표당 BM25F 1회·cosine 1회 그대로입니다. 추가 질의·추가 lane·재검색·reranker 없음.

### 분리의 효과를 저장 점수만으로 측정했습니다

dense 텍스트를 원문 그대로 두면 **dense 벡터가 A와 바이트 동일**하므로, C의 BM25F 배열과 A의 cosine 배열을 융합하면 분리 arm을 정확히 모사할 수 있습니다(새 임베딩 0, 새 검색 0):

| 조건 | FIT@8 | 목표 Hit@8 |
|---|---:|---:|
| A 설치 기준선 | 55 | 28 |
| C 현행(두 lane 공유) | 55 | 29 |
| **D1 = C의 BM25F + A의 dense (lane 분리)** | **56** | **29** |
| D2 = A의 BM25F + C의 dense (dense 단독) | 55 | 29 |

D1은 **회수 4건을 모두 유지하면서 진단된 dense 희석 손실 1건을 정확히 복구**합니다(`cand_727d42f4…` 회복). 남은 손실 3건은 전부 문서 미변경 후보의 부수 밀림입니다. 노출군 기준으로는 **17/30 → 21/30 (+13.3%p)** 입니다.

**대안 비교:** (ㄱ) 현행 append — sparse 이득과 dense 손실이 상쇄, 기각. (ㄴ) **D1 lane 분리, dense=원문 유지** — 비용 0, 효과 확인, **채택 권장**. (ㄷ) dense에 요약 1문장만 추가(별칭 제외) — 41개 재임베딩, dense도 개선될 가능성, D1 다음에 단독 검증. (ㄹ) dense를 요약 중심으로 교체 — 변경이 크고 원문 단서 손실 위험, 이번 범위 밖.

## D. arm 설계 — 질의·문서·융합을 동시에 건드리지 않기

**1순위 arm은 단 하나: D1(lane 분리, dense=원문 유지).** 이유: 효과가 이미 +1/노출군 +13.3%p로 확인됐고, 새 검토 0건·새 임베딩 0건·새 판정 0건이며, 변경 지점이 `project()` 한 함수입니다.

**파라미터·시도 상한:** 이번 라운드 arm 수 **최대 3**(D1 필수, 아래 D1b/Q1은 조건부). RRF k, 가중치, top-k, quota는 **전부 동결**(A2가 이미 무용함을 보임). 문서 레시피는 arm당 **1개 변경만**.

**사전 선택 기준 (결과 보기 전 고정, 낮추지 않음):**
- 주 진단 지표를 **노출군 분모**로 전환: enrich 문서에 연결된 positive 쌍 기준 **A 대비 +10%p 이상**(현재 17/30 → 20/30 이상).
- 보조: 전체 FIT@8이 A 미만이면 실패. 목표 Hit@8 28 이상 유지.
- 비노출군 손실은 **기록하되 실패 조건에서 제외**(전수 적용 시 소멸하는 인공물이므로). 단 손실 건수와 밀어낸 후보의 판정 상태를 반드시 보고.

**126의 재사용 문제 — 진짜 문제입니다.** 126은 이미 여러 라운드 반복 사용됐고, 보조 세트(신규 4요청/8목표, 29쌍)는 A/B/C 모두 29/29로 **포화돼 판별력이 0**입니다. 다만 사용자 목적을 고려하면 값비싼 전수 판정은 필요 없습니다. **제안: 목표 단위 이진 확인.** 새 요청 2~3건(목표 6~10개)을 만들고, 각 목표의 top8에 **"쓸 만한 후보가 1건 이상 있는가"만** 판정합니다. arm 간 합집합을 dedup하면 판정량은 대략 **60~100건**이며, 이는 전수 의미 검토가 아니라 결과 화면 확인 수준입니다. 이 지표는 "틀린 후보는 창작 소재"라는 사용자 철학과 정확히 일치합니다.

## E. 다음 계획 (7단계, CURRENT는 끝까지 유지)

> 공통: 공통 positive 풀 전체(18,180 CID/18,182 RID), 슬롯당 BM25F 1회·cosine 1회, RRF10/CID dedup/top8 동결, Gemini 0, 새 의미 검토는 단계 6에서만, native 원문·조건·효과·권한 변경 0, 전수 데이터 보강은 이번 계획에 **포함하지 않음**.

**1단계 — 진단 아티팩트 고정 (변경 파일: 신규 진단 스크립트 1개 / 새 검색·모델 0)**

**2단계 — lane 분리 계약 (변경 파일: `photo_candidate_documents.py`)**
`project()`가 `text`(dense)와 `fields`(sparse)를 **독립 투영**으로 반환하도록 변경. 토큰 동일성 단언을 **방향성 검사 2개**로 교체: ① dense 투영에 원 D 텍스트가 정확히 prefix로 보존, ② sparse 필드에 원 D 필드 값이 전부 보존되고 추가 값만 append. 정본 hash 불변 검사 유지. 레시피 ID를 `…/v2`로 올리고 기존 v1 재생 경로 보존.
*검증:* 기존 72개 회귀 테스트 + 신규 단위 테스트(분리 불변식, prefix 보존, 필드 소유권). *중단:* 테스트 실패 또는 A 재현 불일치.

**3단계 — D1 실측 (새 임베딩 0, 새 판정 0)**
dense 투영 = 원문, sparse = 기존 보강 41건. 전체 풀 BM25F 75회 + cosine 75회. dense 벡터가 A와 동일함을 hash로 증명하면 cosine은 저장본 재사용 가능.
*사전 기준:* 노출군 ≥20/30, 전체 ≥55/126, 목표 ≥28/40. *기대:* 21/30, 56/126, 29/40.
*중단:* 노출군이 17/30 이하면 2단계 설계를 폐기하고 1단계 진단으로 복귀.

**4단계 — D1b: dense에 요약 1문장만 (조건부, 3단계 통과 시)**
dense 투영 = 원문 + 검토 요약 1문장(**별칭 제외**). 41개만 재임베딩. sparse는 3단계와 동일 → **dense 효과 단독 분리**.
*상한:* 재임베딩 41건, arm 1개, 레시피 변형 1개. *사전 기준:* 노출군이 D1 이상이고 cosine 순위 하락 건수 ≤2. 미달이면 **D1을 최종안으로 확정하고 4단계 폐기**(여러 변형을 더 시도하지 않음).

**5단계 — 0건 목표 12개의 원인 분리 (새 검색·판정 0)**
각 목표에서 최상위 positive의 lane별 순위를 뽑아 "문서형"(한 lane 상위권인데 융합에서 탈락)과 "질의형"(두 lane 모두 심층)으로 분류. **이 단계에서 질의를 바꾸지 않습니다.** 분류 결과만 다음 라운드 입력으로 남깁니다.
*중단 조건 없음(0비용 필수 단계).*

**6단계 — 미사용 목표 기반 소규모 독립 확인 (새 판정 60~100건, 전수 검토 아님)**
새 요청 2~3건·목표 6~10개를 만들고, 승자 arm과 A의 top8만 **목표당 "쓸 만한 후보 1건 이상 존재" 이진 판정**. 126은 개발 진단용, 이 세트는 확인용으로 **역할을 분리하여 기록**.
*사전 기준:* 승자 arm의 목표 충족 수가 A 이상, 그리고 A에서 0건이던 목표 중 최소 1개 회복. *미달:* 운영 적용 보류, CURRENT 유지, 3~4단계 결과는 진단 자산으로만 보존.

**7단계 — 운영 gate와 설치 판단 (CURRENT 유지)**
개발 진단 gate(126 기반)와 **운영 gate를 분리**해 명문화:
- 운영 gate = ① 6단계 독립 확인 통과, ② 40개 목표 중 0건 목표 수가 A보다 **증가하지 않음**, ③ 목표 Hit@8 ≥ A, ④ 전체 FIT@8 ≥ A, ⑤ 72개 회귀 테스트 통과, ⑥ 정본 hash·조건·효과·binding 불변.
- precision·부적합 수·목표별 완전 무회귀는 **gate 아님**(사용자 목적상 틀린 후보는 창작 소재).
- 통과해도 이번 라운드에서는 **새 H-F2 세대 생성까지만**, 설치 선택 갱신은 별도 승인 단계. **native CURRENT는 전 과정에서 변경하지 않음.**

**이번 계획에서 하지 않는 것:** 전수 18,250 보강, RRF/가중치/top-k 탐색, embedding 모델 교체, reranker 추가, 슬롯 태그 사전 필터, 추가 질의·추가 lane, 기준 하향.

## 한 줄 요약

이번 HOLD는 **"보강이 효과 없다"가 아니라 "부분 처리 + 두 lane 공유 문서 + 전체 분모 기준이 겹쳐 효과를 측정할 수 없었다"** 입니다. 가장 싸고 확실한 다음 수는 **lane 분리(D1)** 이고, 그 효과(노출군 17/30→21/30, 전체 55→56)는 이미 저장된 점수만으로 확인됩니다. 융합 튜닝은 측정으로 배제됐고, 전수 보강은 기대 이득 +7~+17의 경계선이므로 **지금 결정하지 말고 D1 확정 후 다시 추정**하는 것이 맞습니다.
