# 검색 준비 캐시와 최신성 관리 적용

2026-10-06. 구현 기준 main은 `cb496c1db984f9fe5d632fa764aae4d3f6aedf63`이다. 기존 후보 원본과 시각 의미 원본, 각각의 16개 벡터 샤드는 유지했다. 검색 결과를 저장하지 않고 슬롯 전용 BM25F 준비 자료를 저장한다.

## 적용한 동작

- `SourceInventory`를 해당 원본의 등록표에서 읽고 후보·프로필·bundle 참조 로딩에 전달한다. 별도 경로의 자료가 설치 경로의 등록표를 빌리지 않는다.
- 슬롯 원본 전체, 실제 로딩한 코드·정책·토크나이저·Python/Unicode 환경으로 캐시 키를 만든다. 같은 ID의 내용 변경도 감지한다. 메모리 캐시도 정책·알고리즘에 결합한다.
- 로컬 원본을 내용 해시로 확인하고, 작성 원본과 필수 인덱스의 검증을 끝낸 독립 세대에 요청을 고정한다. 부분 게시와 늦게 완료한 이전 게시자는 CURRENT를 바꿀 수 없다. 이미 시작한 요청은 이전 세대를 유지한다.
- 새 원본이 아직 검증·게시되지 않았으면 새 요청에 `source_revision_pending`을 반환한다. 필수 원본·인덱스가 무효이면 실패한다. 슬롯 캐시만 누락·손상되면 같은 검증 원본에서 CPU로 다시 계산한다.
- 저장소가 없는 최초 사용은 전체 검증 후 bootstrap한다. 데이터 변경은 정상 유지보수 빌드·검증의 게시 단계로 갱신한다. 코드 변경은 새 CLI/worker를 사용하며, 이미 import한 코드는 reload하지 않는다.
- 공개 팩의 필수 필드는 바꾸지 않는다. 요청별 영수증에 원본 세대와 팩 전체 해시를 기록한다. 감사는 이 세대의 코퍼스에서 슬롯 BM25F를 독립 재계산하고 공개 팩 전체를 다시 비교한다. 같은 팩 bytes가 여러 세대에 대응하면 정확한 영수증 없이 세대를 추측하지 않는다.
- 원격 모드는 명시적으로 선택할 때 새 fetch를 수행하고 실제 commit과 관찰 시각을 기록한다. 런타임 소유 체크아웃을 사용한다. 원격 확인 실패는 `remote_unverified`, 다른 실행 코드가 필요한 경우는 `runtime_restart_required`로 처리한다. 기존 작업 checkout은 자동으로 pull/merge/reset/stash하지 않는다.

기본 저장소는 `~/.cache/image-prompt/photo-runtime`이다. `PHOTO_RUNTIME_STORE` 또는 `--runtime-store`로 변경할 수 있다. `--output-file PACK.json`은 `PACK.json.runtime-receipt.json`도 저장한다. 원격 모드는 `--source-mode remote_before_retrieval --source-remote URL`로 선택한다. 반복 자동 작업은 생성하지 않았다.

장시간 프로세스는 envelope·controls·core·embodiment 검증 후 매 요청 `RuntimeSnapshotProvider.acquire()`를 사용한다. 반환된 handle의 자료는 변경할 수 없으며, 명시적인 deep copy는 독립 코퍼스로 계산한다. 편집자와 요청 프로세스는 동일한 runtime store/namespace를 공유해야 revision/lock 프로토콜이 적용된다. 이 프로토콜 밖의 편집자에게 여러 파일의 논리적 수정 완료까지 보장하지 않는다. 바뀐 원본이 정상 유지보수 검증과 게시를 마쳐야 최신 요청을 처리한다.

## 검증 결과와 범위

실제 파일·두 프로세스의 게시 경쟁·재로딩·영수증·캐시 오류를 검증했다. 원본 해시를 새 값으로 바꾸고 이전 세대를 가리키는 CURRENT도 거부하도록 결합 검사를 추가했다. 새 수명주기 검사 25개가 모두 통과했다. 독립적으로 원래 main 코드에서 생성한 NFKC/슬롯 통계를 `runtime_freshness_v1.json`의 V28 경계로 보존했으며, 관련 캐시 검증 6개도 통과했다. 기존 검색·구조·벡터 샤드 회귀 64개가 통과했다. 기존 V1–V27 기대값은 수정하지 않았다.

[EQUIVALENCE.json](EQUIVALENCE.json)은 main 원본 코드를 별도 프로세스에서 실행한 비교다. 10,088개 슬롯 문서의 전체 인덱스, 24개 동결 입력의 검색 결과/후보 순서/결합 정보/공개 팩 전체/세 시각 의미 블록이 동일했다. 코어도 변경되지 않았다. 실제 임베딩·이미지 API는 호출하지 않았으며, 이미지나 지각 품질을 검증한 결과는 아니다.

준비 시간 3회 측정의 중앙값은 기존 9.55초, 새 경로 9.23초였다. 첫 세대 생성은 22.41초, 이미 게시한 세대를 새 프로세스에서 읽는 두 표본은 9.23초와 8.80초, 같은 프로세스에서 다시 확보하는 표본은 0.12–0.21초였다. 전체 검증을 유지하고 세대 무결성과 객체 변경 방지를 추가한 결과, 현재 CLI의 성능 이득은 작다. 장시간 프로세스에서의 재사용과 최신성/재현 관리에 주된 효과가 있다. 전체 요청·이미지 생성 시간은 이 측정에 포함하지 않았다. OS 파일 캐시는 초기화하지 않았고 다른 검증과 CPU 자원을 공유했다.

현재 주 작업 경로에도 런타임 변경을 적용했고 해당 경로의 자료로 세대 게시와 사전 검증이 성공했다. 첫 적용 시 기존 수정 40개 파일의 원문 해시를 확인했다. 이후 이 중 일부 테스트의 로딩 호출만 명시적인 SourceInventory로 바꿨으며, 원래 기대값과 나머지 내용을 보존했다. 주 작업 경로에만 있는 intellectual 확장도 유지했고 관련 과거 자료 검사 36개가 통과했다. [PRIMARY-APPLICATION.json](PRIMARY-APPLICATION.json)에 기존 대상 파일 백업과 적용 내역을 남겼다. 최초 적용은 커밋 없이 완료했다. 후속 main 병합·푸시 요청은 이 문서의 검증용 작업 트리에서 런타임 범위로 진행하며, 주 작업 폴더의 별도 커밋과 미커밋 자료는 보존한다.

최초 cb496c1d 기반 작업 트리에서는 원래 V27 코드를 보존한 런타임 분기의 V28 경계를 추가했다. 실제 CLI와 독립 영수증 감사의 공개 팩은 V27과 바이트 단위로 동일했다. 이전 V27 실행·변조 검사와 새 V28 경계 검사 13개가 통과했다. 이 main 계보의 등록 변경은 별도 main 작업 트리에 있으며, 이전 main 기반의 주 작업 경로에서는 런타임 코드와 로컬 자료를 검증했다. 두 작업 트리를 같은 main 계보라고 표시하지 않는다.

전체 199개 테스트 파일을 독립 프로세스로 실행했다. 초기 발견 시 1,806개였으며, 이후 추가한 CURRENT 결합 검사와 수정한 로딩·경로 설정의 재검사를 합친 실제 실행 대상은 1,807개다. 전체 결과는 [FULL-REGRESSIONS.json](FULL-REGRESSIONS.json), 실행 범위와 적용 상태는 [VALIDATION.json](VALIDATION.json)에 기록한다. 단일 프로세스 전체 검사는 중단했으므로 통과로 표시하지 않았다.

남은 문제는 수정 전 main 코드와 원래 테스트로도 재현된 세 테스트 메서드다. 유지보수 메타데이터의 `maintenance_only` 오류 1개, 이전 11개 프로필의 내용 보존 비교 실패, liminal 과거 자료의 glass 항목 불일치다. 하위 사례를 포함하면 실패 이벤트 12개와 오류 1개이며 전체 성공으로 표시하지 않는다. 이 문제를 이번 성능·최신성 작업 때문에 기대값을 바꿔서 해소하지 않았다. 관련 원본 재현 기록은 `ORIGINAL-*` 파일에 남겼다. 임시 레지스트리 검사는 SourceInventory.for_test를 명시하고 같은 부정 사례와 기대값을 검사한다.

사용과 유지보수 명령은 `skills/photo-prompt-image-generator/references/maintenance.md`의 Runtime generations 절에 설명했다. 실행 코드가 다른 과거 세대의 감사에는 그 세대의 코드와 호환 Python 환경이 필요하다.

## 후속 main 병합과 게시

원격 main에 색상 설명 정합성을 수정한 `8f9c56b1`이 게시되면서 V28 번호가 겹쳤다. 공개 main의 V28 문서·팩·색상 원본·활성 벡터 샤드는 그대로 보존하고, 런타임 변경을 V29로 이어 붙였다. 최초 런타임 분기의 V28 관찰 기록은 `runtime-branch-v28/`와 원래 V28-RUNTIME-PROOF.json에 별도로 보존했다.

V29의 실제 CLI 공개 팩은 공개 main의 V28 팩과 바이트 단위로 같다. 새 V29 감사·변조 검사, 원래 V28 색상 검사와 V27 이하 과거 경계 검사를 포함한 관련 135개 검사가 통과했고, 사전 검증도 통과했다. [MAIN-MERGE-VALIDATION.json](MAIN-MERGE-VALIDATION.json)과 [MAIN-MERGE-RESOLUTION.json](MAIN-MERGE-RESOLUTION.json)에 결과와 보존 범위를 기록했다. 최초 전체 검사 1,807개에서 재현된 기존 세 실패 종류는 별도 기록으로 유지한다.

게시 범위는 검증용 작업 트리의 런타임 변경과 그 검증 계보다. 주 작업 폴더의 별도 로컬 커밋 두 개와 미커밋·미추적 자료는 이 푸시에 포함하지 않고 보존한다.
