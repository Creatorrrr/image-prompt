# Independent lobed-opening before review

## Conclusion

The before source has a real semantic contradiction in the four-lobed contract: it positively requires exactly four rounded lobes around one opening, but its rejection list names quatrefoil. That rejection wording survives into the publicly emitted optional profile’s opt-in obligation and into its bundle’s confusion boundaries. This is an outward conditional-contract defect; these artifacts do not establish an active hard-profile rejection, deterministic runtime rejection, final-prompt rejection, or image failure.

The intended three-lobe meaning is compatible with the stone case. The intended four-lobe meaning is compatible with the timber-gate case, although that profile’s full outward contract is internally inconsistent. Wrong-count alternatives are incompatible. Both opening profiles are incompatible with the painted-solid-door case, including the four-count profile despite its matching number. The round-opening control exposes neither profile, identity, clarification nor bundle.

## Actual public rejection wording versus full meaning

Both source profiles have byte-identical `semantics.contrast_examples` and `reject_substitutes`, and both bundles have the same `confusion_boundaries`:

1. `쿼트러포일·실제 클로버 잎·대칭 장식 일반과 구별`
2. `세잎·꽃잎 수가 다른 로제트와 구별`

A faithful reading is “distinguish from quatrefoil, actual clover leaves, and generic symmetric ornament,” followed by “distinguish from three leaves / rosettes with a different petal count.” The second phrase is compressed and ambiguous about its grouping; it should not be inflated into a proven categorical rejection of every three-lobed aperture. Actual leaves and generic ornament are sensible distinctions from a specified opening. The unqualified quatrefoil reference is the precise self-rejection problem for the four-lobed opening profile.

The three profile’s positive meaning is “exactly three rounded lobes bound one ornamental opening; the three lobes belong to one continuous opening contour.” Distinguishing it from a four-lobed quatrefoil is count-compatible.

The four profile’s positive meaning is “exactly four rounded lobes bound one ornamental opening; the four lobes belong to one continuous opening contour.” Its source paraphrase, authored components, composition instruction and native-scale render gates all demand that same four-part geometry. Naming quatrefoil as a rejected substitute contradicts that positive shape rather than distinguishing a wrong count or a solid painted representation.

In every pack where the four profile appears, those exact two Korean strings are present at the public visual candidate’s `opt_in_contract.obligation.reject_substitutes`. This proves travel into the outward obligation payload. The same strings also appear in the exposed four bundle’s `confusion_boundaries`. The profile’s `forbidden_prompt_terms`, `runtime_forbidden_labels` and public clarification’s forbidden-label list are empty; the evidence does not show a literal banned-token check or an executed rejection path.

“Compatible” below evaluates the intended positive meaning against the full frozen request and baseline. It does not certify the internally contradictory four-profile contract.

Their full meaning must preserve count, one continuous contour, owner and actual aperture versus solid surface. Adding a separate unrelated opening would also cease to apply the candidate to the requested existing motif/owner.

## Exposure, eligibility, activation, adoption and audit are separate

- Optional appearance: observed as listed in the table. Exact JSON pointers are preserved in `adjudication.json`.
- Runtime eligibility: every exposed target slot candidate is `eligible` from `frozen_core_slot_contract`; every exposed visual profile is `eligible` from `hybrid_visual_profile_resolution`; clarifications are `eligible` contextual candidates; exposed bundles are `eligible` from `all_members_eligible_and_dimensions_open`. Those labels do not establish full semantic compatibility.
- Active hard profile: none of the four candidate packs contains a top-level `visual_obligations` section. The nested obligation is explicitly conditional on `composer_opt_in`. This establishes absence of an active target-profile section in these packs, not a universal activation result for other runs.
- Existing requester-owned hard meaning: `semantic_assertion_obligations` separately preserves each request’s exact count or circle and its through-opening or solid-surface evidence. These required requester assertions are not the optional retrieved profiles.
- Adoption: unobserved. No composed selection, final prompt or promoted contract was provided. The visual selection policy says all candidates are optional, an empty selection list is permitted, and unselected candidates add no prompt or review duty. Semantic clarification separately requires a typed decision for every clarification candidate; its two lobed clarifications are `required_in_final_prompt: false`.
- Final audit and pixels: unobserved and not run. Gate descriptions state prospective review requirements; they are not review results. No image-fidelity conclusion follows.

Inappropriate optional exposure is a retained known limitation: the wrong-count profile/identity is offered on each actual lobed opening, and both opening profiles/identities/bundles are offered for the explicitly painted solid door. Rejecting such options is available to a composer, but their optional status does not make the exposure semantically appropriate. A narrow correction to copied rejection wording must not be described as having fixed this separate exposure problem without new evidence. This review has not inspected any correction.

## Fourth-case admission failure and adapter

The original four-lobed command ended with return code 1 before generating a pack: `Error: authorial core setting needs at least 3 concrete content words`. This is an authorial-core field-admission issue, not a lobed-profile failure, missing retrieval result or image failure. The original `four_lobed_timber.pack.json` is absent.

The candidate-unexposed adapter changed only the authorial core’s `setting` from `A riverside garden` to `a weathered timber gate at a riverside garden`. Independent object comparison confirmed no other core field changed. The new value is an exact contiguous span already present in both raw request and baseline. The ten listed ancillary request/baseline/envelope/control/review/selection/provenance/catalog files are byte-identical between original and adapter, including the unchanged baseline. Original locks and semantic assertions are unchanged. Dependent binding hashes were updated by the author.

The adapter command completed with return code 0 and produced the reviewed fourth pack. For all four reviewed packs, embedded `authorial_core.source_request` and `baseline_prompt_en` equal the original frozen text bytes. The command records report no blocked network attempt. The adapter preserves the intended four-lobed case while making the separate admission repair explicit.
