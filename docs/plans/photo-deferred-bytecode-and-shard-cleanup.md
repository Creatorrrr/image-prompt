# 사진 스킬 보류 bytecode·구 shard 추가 정리 계획

2026-10-19 · 계획 작성 · 실행 전 · 8단계 · 검증 실패·참조 불명확 항목 보류

## 목표와 입력

정확한 재생성이 확인된 bytecode 45개와 구 shard 8세대를 대상으로, 운영·과거
재현에 필요한 원본을 보존하면서 중복 생성물을 정리한다. 모든 후보를 반드시
삭제하는 것이 완료 조건은 아니다. 대상별로 검증 후 정리하거나 근거를 남겨 보류한다.

기준 main은 `d9cb7338deff4f4df07476e5b50b8ff0b3ec6147`이다.
근거는 `docs/research-evidence/photo-prompt/runtime-cleanup-followup-20261019/REPORT.md`와
같은 디렉터리의 `ANALYSIS.json`이다. 계획 작성 시 ANALYSIS.json의 SHA-256은
`9b777b88118e141465a474ecb96a59ad9836878ea6de5197c67fd4cb4bfc559c`다.
실행 시 파일이 달라졌다면 조용히 새 목록으로 교체하지 않고 변경 이유를 확인한다.

검증된 상한은 bytecode 45개/510,854 bytes, shard 8세대/5,770파일/944,439,270
bytes다. 합계는 5,815파일/944,950,124 bytes다. 이를 넘어 대상을 추가하지 않는다.

  재publication, 운영 전환, 원본 workflow/receipt/과거 FREEZE 수정은 하지 않는다.

- Gemini·원격 fallback·새 로컬 추론·새 의미 판정·전수 의미 검토를 실행하지 않는다.

## 1단계 — 실행 기준선과 정확한 allowlist 고정

main·다른 작업 트리의 HEAD/index 및 모든 기존 변경 경로·내용 hash를 수집한다.
CURRENT, 설치 선택, 실제 운영·재현 세대, 모델 lock, 기존 아카이브·분석 파일을
보호 목록에 넣는다. 새 실행 증거는 기존 정리·분석 디렉터리와 별도로 만든다.

후보마다 현재 hash·크기·권한·링크 관계·Git 상태, 원본 소스/복원 위치, 관련
manifest와 실행 참조를 고정한다. 기존 미커밋 경로나 보호 세대와 겹치면 보류한다.
분석 시점 이후 변경된 후보, 이미 없어진 후보는 자동 삭제 성공으로 세지 않는다.

새 실행용 보호 기준선은 이번 의도된 변경 경로를 좁게 구분하는 용도다. 이전
BASELINE/PROTECTED/분석 결과를 덮어쓰지 않고, 기존 보호 목록도 교차 검증한다.

**통과 기준:** 최대 5,815개의 정확한 후보 경로가 확정되고, 보호 목록과의 교집합이
없다. 변경·부재·참조 미해결 항목은 그 이유와 함께 개별 DEFER로 분리된다.

## 2단계 — 원래 경로·bytes를 복구하는 오프라인 수단 검증

bytecode는 Python 3.12.13/3.14.3의 실제 executable·magic, 최적화 설정,
invalidation mode, 원본 header, compiled owner, source SHA를 고정한다.
35개는 현재의 깨끗한 소스, 10개는 기존 EXPERIMENT-LOCK으로 검증한 아카이브
소스를 사용한다. 임시 소스 복사본의 mtime만 원래 header에 맞추고, 재생성한
전체 bytes가 원본과 같아야 한다. 기존 소스·캐시의 mtime은 바꾸지 않는다.

shard는 파일마다 원래 상대 경로/SHA/크기/권한과 Git commit/blob ID,
보존할 봉인 세대의 정확한 파일·manifest를 연결하는 복원 lock을 만든다.
Git 객체에서 추출하는 경로와 봉인 동일본에서 복사하는 경로를 각각 검증한다.
Git 객체가 없는 환경에서 자동 fetch하지 않고, 검증된 다른 복원 수단도 없으면 보류한다.

복원 대상은 아직 없는 임시 루트다. `git checkout/reset`으로 원래 작업 경로를
복원하지 않으며 기존 파일을 덮어쓰지 않는다. 링크를 만들어 봉인 세대와 삭제
대상이 같은 inode를 공유하게 하지 않는다. 현재 있는 복사본과 Git 객체를 활용하고
약 944MB를 새 보관물로 중복 저장하는 방식을 기본으로 삼지 않는다.

필요한 유지보수 도구는 `tools/photo_runtime_maintenance` 아래에만 추가한다.
운영 scripts/precore를 바꾸어 코드 지문을 변경하지 않는다. 경로 이탈·변조·
복원 대상 충돌·누락 멤버를 거부하고, 일부 실패 시 원본을 건드리지 않는지 확인한다.

**통과 기준:** 승인 후보의 파일 전체가 빈 임시 루트에서 원래 상대 경로와 bytes로
복원되고, 의도적 변조·충돌은 거부된다. 복원이 입증되지 않은 항목은 이동하지 않는다.

## 3단계 — 정리 전 운영 기준과 대상별 재현 범위 확정

대상 8세대의 메타데이터/문서/동적 진입점 참조를 재확인하고, 현재 실행 참조와
과거 증거·일회성 통합 참조를 구분한다. 각 세대에 기존 run/receipt 또는 봉인된
과거 validator/실행 증거를 연결한다. 파일 hash 일치만으로 과거 실행 재현을
통과 처리하지 않는다. 실제로 비교 가능한 기존 결과를 확보할 수 없으면 보류한다.

현재 main source inventory/fingerprint를 읽기 전용으로 기록한다. 설치된 H-F2
2개 질의의 전체 풀 18,180 CID/18,182 RID, 실제 1+1 호출, lane 점수·전체 순위,
H/native receipt와 구성 감사, 일반 CLI의 retrieve/view/compose-audit/deliver를
기존 로컬 query 벡터와 독립 run/store 복사본으로 확인한다.

기본 검사는 운영 48개, archive의 저장 전체 순위 450개·실험 테스트 17개,
복원 안전성 검사다. native 70개는 동일 소스/환경의 기존 성공 근거를 확인하고
최종 정리 상태에서 다시 실행한다. 기존 실패가 있다면 원인과 영향 범위를 고정하고,
대상에 연결된 실패를 기준선으로 정당화해 제거하지 않는다.

이전에 위치를 찾은 실행 참조 41건/4세대/7복사본은 보호·복원 매핑에 반영한다.
위치·멤버 SHA 확인을 CLI 재생 성공으로 표현하지 않는다. 41건 전체의 복구를 새
프로젝트로 확대하지 않으며, 정리 대상과 연결된 재현을 확인할 수 없으면 해당 대상만 보류한다.

기존 도구가 과거 증거 디렉터리에 결과를 쓰는 경우 새 출력 경로를 쓰는 유지보수
wrapper를 사용한다. 원본 연구 checkout 읽기, 네트워크, 원본 프로젝트·운영 store
쓰기는 검사 프로세스에서 차단한다. 임시 fixture의 결과만 새 실행 증거로 수집한다.

**통과 기준:** 운영 비교 기준과 대상별 재현 목록/입력/결과 hash가 확보된다.
실행되지 않은 검사와 불명확한 참조가 명시되고, 미해결 대상은 후속 제거에서 빠진다.

## 4단계 — bytecode 45개 격리·검증 후 정리

실행 직전 source/cache SHA, interpreter, ignored/untracked 여부, 보호 충돌,
열린 파일·실행 작업을 다시 확인한다. 아직 조건을 만족하는 정확한 경로만 같은
파일시스템의 이번 작업 전용 격리 위치로 rename하고 이동 journal을 남긴다.

원래 위치에 대상 캐시가 없는 상태에서 운영 48개, 설치 H-F2 2질의/receipt,
archive 450개 순위·17개 테스트를 확인한다. bytecode 쓰기를 차단하여 캐시가
자동 재생성된 상태를 경로 부재 검사로 오인하지 않는다. 보호 hash도 비교한다.

실패하면 이번에 이동한 파일만 원래 위치로 복구한다. 원래 위치에 새 파일이
생겼다면 덮어쓰지 않고 격리본을 유지한 채 관련 항목을 보류한다. 모든 검사를
통과한 파일의 격리본만 제거하며 캐시 디렉터리 전체를 삭제하지 않는다.

**통과 기준:** 정리한 캐시의 원래 경로 부재, 정확한 재생성 수단, 운영·archive
결과 동일성과 보호 파일 보존이 입증된다. 실제 정리 수와 DEFER 수를 구분한다.

## 5단계 — 구 shard 1차 6세대를 세대별로 검증

최대 6세대를 하나씩 진행한다. 각 디렉터리의 전체 멤버가 allowlist와 같고 추가
파일이 없으며 원래/복원본의 hash·권한·링크·열린 파일 조건이 유지되는지 확인한다.
새로운 참조나 파일이 나타난 세대는 즉시 보류한다.

복원 lock을 먼저 검증한 뒤 같은 파일시스템의 전용 위치로 디렉터리를 격리한다.
그 세대에 연결된 과거 재현을 복원한 임시 트리에서 실행하고 기존 결과와 비교한다.
복원 트리 밖의 원래 shard와 연구 checkout을 읽지 못하게 하여 숨은 의존성을 확인한다.

해당 세대의 재현 실패는 그 세대만 충돌 없이 복구하고 보류한다. 성공 대상이
모두 원래 경로에서 빠진 상태에서 main source inventory/fingerprint 동일성,
운영 48개·설치 H-F2·native receipt·일반 CLI·archive 재현과 보호 검사를 확인한다.
공통 검사 실패가 특정 세대에 귀속되지 않으면 그 검사 배치 전체를 복구·보류한다.
배치 검증을 통과한 세대의 격리본만 제거한다.

**통과 기준:** 통과한 세대마다 원래 경로 부재 상태에서 운영과 연결된 과거 재현이
유지되고 두 복원 경로가 유효하다. 설치 봉인, 현재 native layout과 CURRENT는 같다.

## 6단계 — 구 shard 2차 2세대를 개별 검증

`a1f1996d11b6…`, `f82ab43bc2a5…`는 named-phrase 통합의 과거 layout,
native v3/v4 입력·코드·로컬 벡터·판정·manifest·receipt 연결을 먼저 확인한다.
이전 일회성 통합/커밋 스크립트를 원본 checkout에서 실행하거나 과거 결과를
다시 쓰지 않는다. Git commit을 수행하는 스크립트 자체를 재실행하지 않는다.

과거 코드/입력의 임시 복원본과 읽기 전용 재현 도구로, 해당 스크립트가 전제한
멤버 집합과 기존 결과·권한/receipt 계약을 확인한다. 지원되는 기존 재생 경로가
없거나 새 의미 판정·새 추론·원본 절대 경로 변경 없이는 확인할 수 없다면 보류한다.

각각 5단계와 같은 격리·경로 부재·복원·운영/과거 재현 검사를 적용한다.
두 세대의 결과는 독립적으로 기록하며 한 세대의 성공으로 다른 세대를 정리하지 않는다.

**통과 기준:** 각 세대의 관련된 과거 실행과 운영 검사를 별도로 통과한다.
참조 해소나 재현이 불완전하면 해당 세대는 원래 위치에 유지한 채 DEFER로 완료한다.

## 7단계 — 최종 부재 상태에서 운영·재현·복원 종합 확인

실제로 정리한 경로가 모두 없는 상태에서 운영 48개, native/권한/복구 70개,
설치 H-F2의 전체 점수·순위/1+1 호출, H/native receipt·구성 감사, 일반 CLI,
archive 450개 순위·17개 테스트와 복원 안전성을 확인한다. 동일 조건에서 이미
끝난 검사는 입력·코드·환경·대상 부재 상태 hash가 같으면 근거를 재사용하고,
관련 상태가 달라졌거나 실패한 경우에만 필요한 범위를 다시 실행한다.

정리 완료된 shard 전부와 bytecode를 별도 빈 임시 루트에 다시 복원해 정확한
파일 집합/SHA를 확인한다. 복원 후 원래 경로가 다시 생겼다면 동시 작업 여부를
확인하고 이를 이번 삭제 성공으로 처리하지 않는다.

모든 CURRENT와 설치 선택, 보존 세대/모델/receipt, 기존 미커밋 파일과 다른
작업 트리의 내용·상태를 최초 기준선과 대조한다. 삭제가 허용된 정확한 경로만
보호 검사 예외에 넣으며 원래 dirty 파일은 예외에 넣을 수 없다.

**통과 기준:** 추가 회귀나 보호 파일 변화가 없고, 실제 정리된 모든 파일의 복원이
가능하다. 실패하면 이번 변경의 검증된 복원 수단으로만 되돌리고 해당 범위를 보류한다.

## 8단계 — 처리 결과·복원 명령·보류 이유 문서화

정확한 경로/hash와 처리 상태를 GC_DONE/DEFER/UNCHANGED로 기록한다. bytecode
45개와 shard 8세대 각각의 정리/보류 수, 실행한 검사·세대/코드/환경 hash,
복원 수단·명령, 미실행 범위, 보호 검사 결과를 새 리포트에 남긴다.

논리 크기와 실제 공간 변화를 구분한다. 추적 shard가 워킹 트리에서 사라져도
과거 Git 객체와 필수 봉인 복사본은 남는다. Git 이력 재작성·prune·GC로 용량을
추가 확보하는 범위는 포함하지 않는다. 보류 항목이 남아도 실패를 숨기거나
목표 수를 채우기 위해 대상을 확장하지 않는다.

후속 실행에서 단계별 커밋을 요청받으면 각 단계 구현·검증 후 이번 도구/문서와
통과한 정확한 삭제 경로만 stage한다. 기존 미커밋 분석 자료 등은 자동 포함하지
않으며 index diff를 검토한다. bytecode는 ignored 파일이므로 삭제 자체는 Git
diff에 나타나지 않고 실행 journal/검증 결과로 증명한다. push는 별도 요청을 따른다.

**완료 기준:** 모든 대상의 정리 또는 보류 근거와 복원 방법이 확인되고 H 단독+F2,
과거 재현 원본, 미커밋 작업, 모든 CURRENT가 유지된다. 이번 문서 작성은 계획이며
격리·삭제·도구 구현·커밋을 실행한 결과가 아니다.
