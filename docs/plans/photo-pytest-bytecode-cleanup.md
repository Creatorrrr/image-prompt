## 목표와 고정 입력

분석에서 원본 전체 bytes 재생성이 확인된 pytest cache **최대 65개 / 807,566
bytes**만 대상으로 한다. 복구·참조·파일 부재 상태의 회귀 검증을 통과한 항목만
정리하고, 실패하거나 참조가 불명확한 항목은 보존한다. 전부 삭제하는 것이 완료
조건은 아니다.

근거는 `docs/research-evidence/photo-prompt/runtime-cleanup-final-deferred-20261019`의
`REPORT.md`, `ANALYSIS.json`, `PYTEST-PROBE.json`, `PYTEST-RECHECK.json`이다.
현재 main은 `966c7e91534521b04887e086ed6d2716de994a8e`다.

실행 시 상태가 달라진 항목은 다른 배치로 옮기지 않고 보류한다.

## 1단계 — 정확한 65개와 보호 기준선 고정

입력 SHA와 세 근거 파일의 후보 집합·65개/807,566 bytes·A/B 배분이 일치하는지
확인한다. 경로별 cache/source SHA, 크기·권한·inode·link, Git/ignored 상태,
compiled filename, 원래 header·mtime·source 크기와 출처를 고정한다.

두 작업 트리의 HEAD/index/staged diff와 기존 변경 경로·내용, CURRENT 전체,
설치 선택, 실제 선택 세대·소스·모델·환경·receipt를 보호한다. 실행 직전의 새 작업도
포함한다. 기존 보호 기준선과 승인된 이전 삭제 기록을 읽고, 추가 보호 파일만 별도
변경분으로 기록한다. 작은 캐시 정리를 위해 전체 기준선·원본 store를 중복 복제하지 않는다.

캐시가 기존 보호 목록에 있다는 이유로 전체 보호 검사를 해제하지 않는다. 이번에
실제로 격리한 정확한 경로만 개별 예외로 기록한다. 원래 dirty 파일이나 그 소스와
겹치면 예외로 넣지 않고 보류한다.

**통과 기준:** 입력과 allowlist가 고정되고 보호 목록이 완성된다. 변경·부재·링크·
미커밋 중첩 항목은 DEFER로 기록하며, 대상 밖 파일이 추가되지 않는다.

## 2단계 — 소비 경로와 소스·pytest 재생성 재검증

현재 코드, 알려진 봉인·아카이브 소스, 관련 run binding에서 정확한 cache 경로와
소비 경로를 확인한다. 일반 import, pytest cache 읽기, 동적/sourceless loader,
직접 `.pyc` 실행과 marshal 사용을 구분한다. 진단용 경로 목록과 실행 의존성을
혼동하지 않는다. 관련 opaque archive나 외부 소비 경로를 해소하지 못하면 보류한다.
기존 미해결 실행 41건 전체의 복원으로 확대하지 않는다.

A도 현재 파일만을 복원 원천으로 삼지 않는다. 일치한 소스를 Git commit/tree 경로·
blob·SHA에 연결하거나, 해당 소스의 별도 복원 봉인을 확보한다. B의 과거 blob도
도달 가능한 로컬 commit에 연결하고 객체를 검증한다. 누락 객체를 자동 fetch하지 않는다.

Python 실행 파일·버전·magic·cache tag, pytest 9.0.3과 사용한 rewrite 구현·의존성
지문, 최적화·invalidation 설정을 lock으로 고정한다. 이전 불일치의 원인이었던 AST
수명 차이를 재현기에 남기지 않는다. private 임시 원문과 원래 compiled filename·
mtime을 사용해 pytest 자체 `_rewrite_test`/`_write_pyc_fp`로 전체 bytes를 비교한다.
원본 cache나 테스트 모듈을 import/실행하거나 source/mtime을 변경하지 않는다.

**통과 기준:** 통과 후보의 참조·출처·도구가 확인되고 원본 전체 bytes가 재생성된다.
pytest 버전 문자열이나 코드 속성 일부가 같다는 이유만으로 PASS하지 않는다.

## 3단계 — 원본-byte ZIP과 재컴파일 복원 검증

통과 후보만 작은 원본-byte recovery ZIP으로 보존한다. ZIP 자체와 파일별 상대
경로·SHA·크기·권한을 lock으로 고정하고, 소스·도구 lock은 중복을 줄여 기록한다.
복원 도구는 기존 미커밋 분석 파일이 없어도 실행 증거만으로 동작해야 한다.

아직 없는 임시 루트에서 두 경로를 독립 검증한다.

- 원본-byte ZIP: Git 객체·원문·원래 Python/pytest 환경을 읽을 수 없는 상태에서도
  정확한 bytes·권한·경로로 복원한다. 정상 복원용 Python·도구 외 역사 환경에 의존하지 않는다.
- 재컴파일: 고정한 소스와 Python/pytest 구현으로 원래 header·compiled filename을
  포함해 전체 bytes를 재생성한다. 원래 cache나 격리본을 입력으로 사용하지 않는다.

경로 이탈·절대 member·중복/대소문자 또는 Unicode 정규화 충돌·symlink·변조·
누락·기존 목적지와 동시 생성 파일을 거부하는 검사를 수행한다. private 임시 트리에서
완성한 뒤 덮어쓰기 없는 방식으로 게시하며, 부분 실패도 기존 파일을 변경하지 않는다.
복원된 cache 본문은 실행하지 않는다.

**통과 기준:** 통과 대상 전체의 두 복구 수단과 충돌·변조·부분 실패 처리가 확인된다.
복원 가능성이 미입증인 파일은 이동하지 않는다.

## 4단계 — 정리 전 운영·과거 재현 기준 확보

현재 working source/code/model·선택 세대·입력·환경 지문을 기록한다. 운영 48개,
실제 설치 H-F2 2개 목표의 원래 점수·전체 순위와 실제 1+1 검색 호출, H/native
receipt·구성 감사, 일반 CLI retrieve/view/compose-audit/deliver의 비교 기준을 확보한다.
과거/최신 archive의 저장 순위 225+225개와 선택한 실험 테스트 17개도 범위를 명시한다.
기존 HOLD를 PASS로 바꾸지 않는다.

원본 대신 private 임시 store/run을 사용하고 네트워크·원래 프로젝트/운영 store
쓰기를 차단한다. cache 자동 쓰기와 격리본·원래 연구 checkout을 통한 우회 읽기를
막는다. 원래 CURRENT와 임시 fixture의 pointer를 구분한다. 실제 pytest writer와
cache 읽기/재생성 계약도 private 파일로 확인하며, 65개 테스트 전체를 무조건
실행하거나 비활성 평가를 다시 활성화하는 범위로 확대하지 않는다.

동일 코드·입력·환경의 성공 근거는 지문과 범위가 같을 때 재사용한다. 단, 최종
대상 부재 상태의 검증을 정리 전 PASS로 대체하지 않는다. 긴 native/권한/전달·
복구 70개는 최종 합산 부재 상태에서 한 번 확인하도록 배치한다.

**통과 기준:** 비교 가능한 운영·설치·역사 재현 기준과 sandbox 범위가 확보된다.
실패가 있으면 원인과 관련 후보를 보류하며, 공통 상태가 불명확하면 이동하지 않는다.

## 5단계 — 배치 A 최대 47개 격리와 부재 검증

이동 직전에 cache/source hash·권한·link·Git 상태·열린 파일과 작업 상태를 다시
확인한다. 현재 source가 수정됐거나 새 작업과 겹친 항목은 보류한다. allowlist의
파일만 같은 파일시스템의 새 전용 경로로 원자적으로 이동하고 journal에 기록한다.

원래 경로가 없는 상태에서 운영·설치 H-F2/receipt·일반 CLI·archive 재현과 보호
검사를 수행한다. 검증 프로세스가 원래 cache·격리본을 읽거나 cache를 재생성해
원래 위치에 쓰지 못하게 한다. source·metadata·CURRENT는 바꾸지 않는다.

실패하면 이번에 이동한 파일만 복구한다. 원래 위치에 동시 작업 파일이 생겼으면
덮어쓰지 않고 격리본과 충돌 기록을 보존한다. 원인 귀속이 불명확하면 배치 전체를
보류한다. 통과한 격리본도 7단계까지 제거하지 않는다.

**통과 기준:** A 통과 대상의 실제 부재와 운영·재현 동일성·보호 상태가 확인된다.
다음 배치 전에 공통 운영/보호 상태가 정상임을 확인한다.

## 6단계 — 배치 B 최대 18개 격리와 합산 부재 검증

현재 source를 과거 버전으로 되돌리지 않는다. 과거 Git 원문은 복원 검증용 private
경로에서만 사용한다. 고정한 B의 참조·소스 lock과 파일 상태를 다시 확인한 뒤
5단계와 같은 preflight·원자적 이동·journal·읽기/쓰기 차단을 적용한다.

A 통과 대상과 B 통과 대상이 함께 원래 경로에 없는 상태에서 운영·설치·CLI·
archive·pytest cache 계약과 보호 상태를 확인한다. 실패 영향이 분명한 묶음만
개별 복구하며, 불명확하면 영향받는 배치 전체를 복구·보류한다. 동시 작업 파일은
덮어쓰지 않는다. 공통 실패가 해결되지 않으면 추가 정리를 계속하지 않는다.

**통과 기준:** 합산 부재 상태에서도 비교 결과와 보호 조건이 유지된다. 통과한
격리본은 최종 검증까지 보존하고, 미검증 과거 실행 전체의 성공을 주장하지 않는다.

## 7단계 — 최종 합산 부재·오프라인 복구 검증 후 제거

통과 대상 전체가 원래 경로에 없는 상태에서 native·권한·전달·복구 70개를 확인한다.
운영 48개·실제 설치 H-F2/receipt·일반 CLI·archive·pytest 계약은 동일한 부재/차단
조건에서 통과한 결과와 지문을 대조하고, 새 변경·실패·미해결 우려가 있을 때만
관련 검사를 반복한다.

원래 cache와 격리본을 읽을 수 없는 상태에서 ZIP 복원과 재컴파일을 다시 검증한다.
ZIP 경로는 Git·원문·역사 도구 환경까지 차단해 독립성을 확인한다. 모든 CURRENT·
설치 선택·기존 dirty/staged/untracked·다른 작업 트리·남은 21개와 나머지 보호
범위를 최초 기준선과 비교한다. 실제 승인된 격리 경로 외 예외를 추가하지 않는다.

모든 gate를 통과한 뒤 격리본의 정확한 집합·SHA·권한·link를 재확인하고 해당
파일만 제거한다. `__pycache__` glob이나 디렉터리 전체를 삭제하지 않는다. 예상하지
못한 파일·하위 디렉터리·동시 생성이 있으면 제거를 중단하고 보류한다.

최종 원래/격리 경로 부재, 다른 파일 보존과 실제 제거 수를 확인한다. 중간 오류는
검증된 복구 수단과 journal로 처리하며, 동시 생성 파일이나 기존 복구 증거를
덮어쓰지 않는다. 보류된 충돌에는 복구 위치와 남은 수동 처리 사항을 명시한다.

**통과 기준:** 실제 정리한 파일 모두가 정확히 복구 가능하고 운영·재현·보호
조건을 만족한다. 실패나 참조 불명확을 숨기기 위한 범위 확대는 하지 않는다.

## 8단계 — 처리 결과·복원 명령·증거와 커밋 범위 정리

고정 후보 65개를 실제 정리/사전 보류/복구 후 보류/충돌 보존으로 빠짐없이 설명한다.
경로별 원인, 실제 제거 수·논리 bytes·배치·소스/Python/pytest/ZIP lock, 실행한
검사와 미실행 범위를 기록한다. 복원과 재검증 명령은 새 목적지/출력 경로를 사용한다.

논리 제거 상한 807,566 bytes와 새 archive·도구·증거의 추가 크기를 함께 보고한다.
