# Git 과거 소스로 재현한 bytecode 228개 추가 정리 계획

2026-10-19 · 8단계 실행 완료 · bytecode 228개 정리 · H 단독+F2/CURRENT 유지

실행 결과: `docs/research-evidence/photo-prompt/runtime-bytecode-cleanup-20261019/REPORT.md`.
아래 계획의 실제 처리·보존·검증 결과와 복원 명령은 실행 리포트를 따른다.

## 목표와 고정 입력

분석에서 전체 bytes 재생성이 확인된 bytecode 최대 228개만 대상으로 한다.
운영·과거 재현·복원 검사를 통과한 파일은 정리하고, 실패하거나 참조가 불명확한
파일은 원래 위치에 보존한다. 228개 전부 삭제하는 것이 완료 조건은 아니다.

근거 디렉터리는 `docs/research-evidence/photo-prompt/runtime-cleanup-remaining-20261019`다.
`ANALYSIS.json` 중 `bytecodes[].new_status == EXACT_GIT_SOURCE`인 경로만 사용한다.
작성 시 입력 SHA-256은 다음과 같다.

`72babbafdb1391bd1069597a0e4a3825e9d64c0bfabb5f1af01caf52a2e49519`

현재 main은 `2aceff1d9a0c2a7a0189be1bf4500e3ce725cfd8`이다. 분석의 독립 재검증은
Python 3.12.13에서 18개, 3.14.3에서 210개가 PASS다. 이는 정확한 재컴파일의
근거이며, 원래 경로가 없는 상태의 운영·과거 재현 성공 근거는 아직 아니다.

| 배치 | 원래 source의 현재 상태 | 파일 상한 | 논리 bytes | Python 3.12 / 3.14 |
|---|---|---:|---:|---:|
| A | 현재 source 파일이 있음 | 25 | 807,269 | 13 / 12 |
| B | 현재 source가 없고 과거 Git 소스로 재현 | 203 | 4,256,525 | 5 / 198 |
| 합계 | | 228 | 5,063,794 | 18 / 210 |

A도 현재 source가 cache의 원래 revision과 같다고 가정하지 않는다. 두 배치 모두
고정한 Git blob/SHA·원래 header·compiled filename으로 재생성한다.
실행 때 파일 상태가 달라지면 자동으로 배치를 다시 배분하지 않고 해당 파일을 보류한다.

## 반드시 보존할 범위

- H 단독+F2의 공통 positive 풀 전체 검색, 단일 query, 슬롯당 BM25F 1회·로컬
  임베딩/cosine 검색 1회, F2/RRF10/top8/CID 중복 제거를 유지한다.
- 현재 설치 선택 `retrieval-runtime.json`, H 세대 `663038595155…`, native 세대
  `9649504ffbcd…`, 운영 코드 지문 `493f1830db1f…`, 봉인 코드 94개·모델·Python·
  receipt·receipt index·기존 실행 결과를 그대로 둔다. 전체 ID는 입력 JSON을 따른다.
- 알려진 CURRENT 168개와 실행 직전 추가 발견한 CURRENT 모두를 보호한다.
  설치·publish·모델 재구축·CURRENT 전환·원본 workflow/receipt/FREEZE 수정은 하지 않는다.
- main과 다른 작업 트리의 원래 modified/staged/untracked 파일 내용과 Git 상태를
  보존한다. 직전 분석 디렉터리의 미커밋 7파일도 기존 작업으로 취급한다.
- 나머지 bytecode 86개(미커밋 source 연결 5개, 재생성 미입증 15개, pytest cache
  66개), root shard 5세대, 공용·유지보수 모듈 4개, 모든 역사 store·아카이브와
  다른 작업 트리, 사용자 이미지·프롬프트·ledger·고유 리뷰·판정·vector를 유지한다.
- Git 이력 재작성·GC/prune·stash/reset/clean·광범위 stage를 하지 않는다.
  보존 조건을 통과시키기 위해 기존 파일을 되돌리거나 CURRENT를 교체하지 않는다.
- Gemini·원격 fallback·새 로컬 임베딩 추론·새 의미 판정은 호출하지 않는다.
  검증에는 저장된 query vector·점수·순위·판정과 독립 임시 복사본을 사용한다.

새 실행 증거는 기존 분석·완료 기록과 다른 디렉터리에 만든다. 기존 freeze/prove/GC
단계를 재실행하거나 BASELINE·REMOVED·기존 검사 결과를 덮어쓰지 않는다.
필요한 도구는 `tools/photo_runtime_maintenance` 아래 별도 유지보수 도구로 추가하고,
운영 scripts/precore를 바꾸지 않는다.

## 1단계 — 보호 기준선과 정확한 후보 목록 고정

실행 직전 두 작업 트리의 HEAD/index/staged diff와 기존 변경 경로·내용 hash,
모든 CURRENT, 설치 선택, 실제 선택 세대·모델·코드·receipt를 기록한다. 직전의
보호 근거와 대조하고, 계획 작성 후 생긴 작업도 보존 대상에 포함한다.

입력 SHA와 후보 228개/5,063,794 bytes를 대조한다. 경로별 cache SHA·크기·권한·
inode·link 수·Git/ignored 상태, source 경로·현재 존재 여부·compiled filename,
원래 header와 분석 배치를 고정한다. 정확한 상대 경로만 allowlist에 넣는다.

기존 보호 목록에 이번 cache가 들어 있다는 이유로 보호 검사 전체를 해제하지 않는다.
새 실행기에서는 실제로 격리·정리한 허용 경로만 개별 예외로 기록하고 나머지는
계속 비교한다. 원래 dirty 파일은 예외로 넣을 수 없다. 기존 기준선은 수정하지 않는다.

**통과 기준:** 후보 상한·입력 hash·보호 목록이 확정된다. 변경·부재·링크·기존 작업
중첩 항목은 개별 DEFER로 빠지고, 나머지 86개 등 대상 밖 파일은 포함되지 않는다.

## 2단계 — 소비 경로와 Git 출처·재생성 재검증

현재 코드·알려진 봉인/아카이브 소스·기존 run binding에서 해당 cache 경로와 module
소비 경로를 확인한다. 일반 import 외에 동적 loader, sourceless loader, 직접 `.pyc`
실행, marshal 사용, 절대 경로 참조도 구분한다. 보존 목록에 경로가 적혀 있는 것과
실제 실행 의존성을 구분하며, 확인하지 못한 참조를 미참조로 간주하지 않는다.

과거 실행에 필요한 cache-only 입력이거나 참조를 해소할 수 없는 파일은 보류한다.
기존 미해결 실행 41건 전체를 복구하는 작업으로 확대하지 않고, 이번 후보와 연결된
범위만 조사한다. opaque archive의 관련 참조가 불명확하면 해당 후보를 보류한다.

후보별로 source가 포함된 Git commit/tree 경로와 blob ID·SHA-256을 복원 lock에
연결하고 로컬 객체를 검증한다. 적합한 Python executable·버전·magic·cache tag와
최적화/invalidation 설정을 기록한다. compiled filename이 상대 경로인 1개는
분석 때 확인한 문자열을 그대로 사용한다.

원래 mtime은 임시 source 복사본에만 적용한다. 원본 cache·source를 실행하거나
수정하지 않고 전체 cache bytes를 비교한다. 객체가 없으면 자동 fetch하지 않는다.
도달 가능한 이력 밖의 추정 source를 만들어 일치하는 것으로 처리하지 않는다.

**통과 기준:** 통과 후보 모두의 소비 경로·Git 출처·전체 bytes 재생성이 확인된다.
출처·참조·interpreter가 불확실한 파일은 원래 위치에 유지한다.

## 3단계 — 원본 bytes 복구 묶음과 안전한 복원 검증

통과 후보의 원본 cache bytes를 작은 recovery ZIP에 보존한다. 파일별 상대 경로·
SHA·크기·권한과 ZIP 자체 SHA를 lock으로 고정한다. 압축 크기는 생성 후 측정한다.
같은 source blob은 중복 기록하지 않고, 기존 Git 이력과 봉인 코드를 복제하지 않는다.

아직 없는 임시 루트에서 두 경로를 검증한다. 하나는 원본-byte ZIP 복원이고,
다른 하나는 로컬 Git source와 고정한 Python으로 재컴파일하는 경로다. 두 결과의
전체 파일 집합·원래 상대 경로·bytes·권한을 비교한다. Git 객체나 interpreter를
사용할 수 없는 조건에서도 ZIP 복원 경로는 독립적으로 동작해야 한다.

복원 도구는 경로 이탈·절대 archive member·중복/충돌 member·symlink·변조·누락을
거부한다. 기존 목적지와 복원 도중 생긴 파일을 덮어쓰지 않고, 부분 실패 시 이번
임시 산출물만 처리한다. cache 본문을 import/실행하여 복원을 시험하지 않는다.

**통과 기준:** 대상 전체의 두 복구 수단과 변조·충돌 거부가 검증된다. 검증하지 못한
파일은 이동하지 않는다. 이미 존재하는 복구 묶음이나 과거 lock을 덮어쓰지 않는다.

## 4단계 — 정리 전 운영·과거 재현 기준 확보

현재 working source/code/model·선택 세대·환경 지문을 기록한다. 기본 운영 검사
48개, 실제 설치 H-F2 2개 목표, H/native receipt·구성 감사, 일반 CLI의 기존
view 및 새 retrieve/view/compose-audit/deliver를 독립 임시 store/run에서 확인한다.

H-F2는 공통 positive 풀 18,180 CID/18,182 RID, 실제 1+1 검색 호출, 원래 lane
점수·전체 순위를 비교한다. 과거/최신 archive의 저장 순위 225+225개와 실험
테스트 17개도 원래 입력·판정으로 비교한다. HOLD 판정을 PASS로 바꾸지 않는다.

새 wrapper/output을 사용해 예전 검사 산출물을 덮어쓰지 않는다. 네트워크·원래
프로젝트/운영 store 쓰기와 원래 연구 checkout 읽기를 차단한다. cache 자동 쓰기를
막고 원래 CURRENT와 임시 fixture pointer를 구분한다.

동일 코드·입력·환경의 성공 근거는 지문을 대조해 재사용한다. 최종 부재 상태에서
확인할 native/권한/복구 70개는 7단계에서 한 번 실행하도록 배치한다.

**통과 기준:** 운영·설치·archive의 비교 가능한 기준과 검사 범위가 확보된다.
실패를 이번 삭제의 정상 기준으로 정당화하지 않고 관련 후보를 보류한다.

## 5단계 — 배치 A 최대 25개 격리·부재 검증

실행 직전 candidate/source hash·권한·link·Git 상태·열린 파일과 작업 상태를 다시
확인한다. 불확실한 항목은 빠진다. allowlist에 있는 파일만 같은 파일시스템의 새
전용 격리 경로로 원자적으로 이동하고, 이동 전후 경로·hash·상태를 journal에 남긴다.

원래 경로가 없는 상태에서 운영 48개·실제 설치 H-F2/receipt·일반 CLI·archive
재현과 보호 검사를 확인한다. 검증 프로세스가 원래 cache 및 격리본을 읽거나
원래 cache를 다시 쓰지 못하게 한다. source 파일과 metadata는 바꾸지 않는다.

실패 시 이번에 옮긴 파일만 되돌린다. 원래 경로에 동시 작업 파일이 생겼으면
덮어쓰지 않고 격리본을 남긴 채 보류한다. 원인 귀속이 불명확하면 배치 전체를
보류한다. 통과 파일의 격리본도 7단계 종합 검증 전에는 제거하지 않는다.

**통과 기준:** 통과 대상의 원래 경로 부재, 운영·재현 동일성과 보호 상태가 입증된다.
복원/충돌/보류 결과가 개별 기록되고 다음 배치 전 공통 상태가 정상임을 확인한다.

## 6단계 — 배치 B 최대 203개 격리·부재 검증

현재 source가 없으므로 cache-only 소비 경로와 Git 복원 lock을 다시 대조한다.
과거 source를 현재 운영 source 위치에 다시 놓거나 오래된 테스트/도구를 운영으로
복귀시키지 않는다. 명확히 닫힌 참조 범위의 파일만 격리한다.

5단계의 preflight·원자적 이동·journal·원래/격리 경로 읽기 차단과 회귀 검증을
동일하게 적용한다. A 통과 대상까지 함께 원래 경로에서 빠진 상태로 검사한다.
의존성이 다른 묶음은 분리하고, 실패 영향이 불명확하면 해당 묶음을 복구·보류한다.

공통 운영/보호 상태의 실패가 해결되지 않으면 추가 정리를 계속하지 않는다.
동시 작업 파일을 덮어써 회복하지 않으며, 통과한 격리본은 최종 단계까지 유지한다.

**통과 기준:** B의 통과 대상과 A를 합친 부재 상태에서 운영·과거 재현이 유지된다.
누락된 source나 확인하지 못한 과거 실행을 검사 성공으로 확대하지 않는다.

## 7단계 — 최종 부재 상태 검증 후 격리본 정리

이번 통과 대상 전부가 원래 경로에 없는 상태에서 native·권한·전달·복구 70개를
확인하고, 운영 48개·실제 설치 검색/receipt·일반 CLI·archive 결과와 코드·모델·
입력·환경 지문을 대조한다. 같은 부재·차단 조건으로 이미 통과한 검사는 근거를
재사용하며, 상태 변경이나 실패가 있을 때만 관련 범위를 다시 실행한다.

원래 cache와 격리본을 사용할 수 없는 임시 환경에서 ZIP 복원과 Git 재컴파일을
다시 검증한다. SHA만 일치한다는 이유로 실제 운영·재현 검사를 생략하지 않는다.
모든 CURRENT·설치 선택·원래 dirty/다른 작업 트리·보류 86개와 나머지 보호 파일을
최초 기준선과 비교한다. 이번 실제 격리 경로만 의도된 차이로 인정한다.

모든 검증 후 격리 디렉터리의 파일 집합·hash·권한·link를 재확인하고, 검증된 이번
격리본만 제거한다. 디렉터리 전체나 `__pycache__` glob을 삭제 대상으로 삼지 않는다.
최종 경로 부재와 보호 상태를 다시 확인하고, 다른 파일·새 cache가 생겼으면 이번
삭제 성공으로 세지 않는다. 오류 시 검증된 복구 수단으로만 복구하고 충돌은 보류한다.

**통과 기준:** 실제 정리한 파일 전부가 정확히 복구 가능하며 원래/격리 경로 부재,
운영·재현 동일성과 보호 상태가 확인된다. 실패를 숨기기 위한 범위 확대는 없다.

## 8단계 — 결과·복원 명령·보류 이유와 커밋 범위 정리

후보 228개를 정리 완료/복구 후 보류/사전 보류 등으로 모두 설명하고, 실제 정리
수·bytes·배치·cache/source/Git/interpreter/ZIP hash와 실행한 검사·미실행 범위를
기록한다. 재검증 명령은 새 출력 경로를 사용하며, 복원은 기존 파일을 덮어쓰지 않는다.

논리 삭제 크기 5,063,794 bytes 상한과 recovery ZIP·증거 추가 크기를 구분한다.
APFS 공유 블록과 Git 이력을 고려하지 않은 수치를 물리 확보 공간으로 표현하지 않는다.
이전 158개·45개 cache와 구 shard 8세대를 이번 성과로 중복 집계하지 않는다.

실행 단계에서 커밋이 요청되면 각 단계 검증 후 승인된 계획·새 유지보수 도구·
이번 실행 증거만 명시적으로 stage한다. ignored cache 삭제 자체는 Git diff에
나타나지 않으므로 경로 부재·journal·hash·복구 검사로 증명한다. 직전 분석 7파일과
다른 미커밋 작업은 자동 stage하지 않고 index diff를 검토한다. push는 별도 요청을 따른다.
